Zero-Shot and Few-Shot Prompting

Large language models emerge from pretraining with the ability to perform a remarkable variety of tasks purely from a natural-language description or a small set of demonstrations embedded in the prompt — no gradient updates required. This property, called in-context learning (ICL), divides into two regimes: zero-shot prompting, where the model receives only a task description and must generalise from its pretraining distribution, and few-shot prompting, where the model receives k labelled input–output pairs ("shots") that illustrate the task format before seeing the target input. Understanding when each regime works, why ICL succeeds at all, and how to design prompts that maximise accuracy is the foundation of practical LLM engineering. The behaviour is surprisingly sensitive to prompt wording, example ordering, label distribution, and output format — effects that can swing accuracy by ±15 percentage points on the same underlying model and the same test inputs.

Overview

Brown et al. (2020) introduced GPT-3 with the observation that large language models can perform tasks from examples in the prompt without any weight updates — a capability dubbed in-context learning. Zero-shot prompting asks the model to solve a task without any examples, relying entirely on pretraining knowledge and the ability to parse the task description. Few-shot prompting provides k demonstrations (typically 1–16) of the (input, output) mapping to anchor predictions. Both approaches work because the LLM has been pretrained on text that implicitly encodes many task formats; the prompt activates the right behavioural mode. Few-shot ICL is not fine-tuning — no gradient computation occurs — but it consistently improves accuracy, particularly on tasks whose output format differs from natural prose (classification labels, structured outputs, mathematical answers). The performance gap between zero-shot and few-shot prompting narrows as models grow larger, and instruction-tuned models close much of this gap at zero-shot by learning to follow explicit task descriptions from human-feedback training.

Zero-Shot Prompting

In zero-shot prompting, the prompt contains only a task description and the input — no demonstrations. The model must infer the correct output format and decision boundary from the task description alone. For simple, well-represented tasks (translation, summarisation, QA), zero-shot prompting with instruction-tuned models performs surprisingly well. For more exotic tasks (structured extraction, constrained generation, multi-step classification), zero-shot performance degrades because the model's prior over output formats may not match the desired format. Effective zero-shot prompting requires precise task descriptions: specifying the output format explicitly ("Reply with exactly one word: Positive or Negative"), setting appropriate constraints ("Do not explain your reasoning"), and where relevant, priming with a role ("You are an expert sentiment analyst"). Instruction-tuned models such as GPT-4o, Claude 3, and Gemini 1.5 handle zero-shot prompting far better than base language models because they have been explicitly trained on a diverse distribution of instructions and the corresponding outputs expected from a helpful assistant.

import openai

client = openai.OpenAI()

SYSTEM = "Classify sentiment. Reply with one word: Positive or Negative."
POOL = [("This film was absolutely fantastic!", "Positive"),
        ("I hated every minute of it.", "Negative"),
        ("An incredible, emotionally resonant performance.", "Positive"),
        ("Boring, predictable, and painfully slow.", "Negative"),
        ("One of the best films I have seen.", "Positive"),
        ("A complete waste of two hours.", "Negative"),
        ("Breathtaking cinematography and tight script.", "Positive"),
        ("Dreadful acting and a nonsensical plot.", "Negative")]
TESTS = [("Superb acting and a gripping story.", "Positive"),
         ("Disappointing direction and flat characters.", "Negative")]

def classify(text, k):
    msgs = [{"role": "system", "content": SYSTEM}]
    for inp, lbl in POOL[:k]:
        msgs += [{"role": "user", "content": inp}, {"role": "assistant", "content": lbl}]
    msgs.append({"role": "user", "content": text})
    resp = client.chat.completions.create(model="gpt-4o-mini", messages=msgs, max_tokens=3)
    return resp.choices[0].message.content.strip()

for k in [0, 1, 2, 4, 8]:
    acc = sum(classify(t, k) == l for t, l in TESTS) / len(TESTS)
    print(f"k={k}-shot  accuracy={acc:.2f}")

The zero-shot case (k=0) already achieves strong results on sentiment classification with instruction-tuned models because the task is well-represented in pretraining and the system prompt is explicit. As k increases from 0 to 4, accuracy typically improves by 5–15 percentage points on classification tasks. Gains diminish sharply past k=4, and at k=8 the marginal benefit of additional shots is rarely worth the token cost. The main cost of few-shot prompting is tokens: 8 examples at 25 tokens each adds 200 tokens to every API call, increasing latency and spend on high-volume deployments. For a 10 million API call per day system, reducing from 8-shot to 4-shot can yield meaningful cost savings with minimal accuracy loss on standard tasks.

Few-Shot In-Context Learning

Few-shot in-context learning provides the model with k (input, output) demonstration pairs before the target input. The demonstrations serve multiple functions: they anchor the output format (showing what "Positive" vs "Negative" looks like), shift the model's prior toward the task distribution (suppressing off-task generations), and reduce ambiguity in the task description. ICL does not update model weights — the demonstrations are processed as ordinary tokens in the context window. Multiple theories attempt to explain why ICL works: (1) the task description and examples together retrieve a latent representation of the task from the LLM's pretrained knowledge; (2) the model performs implicit gradient descent in its forward pass, simulating one step of fine-tuning; (3) examples simply serve as a format anchor without changing the model's underlying task computation. The sensitivity of ICL to label correctness is informative: replacing all labels with random labels degrades accuracy by only 5–15% on many tasks, suggesting the model relies more on format structure than the semantic content of labels. This finding has major implications for prompt engineering — the choice of which examples to include matters more than ensuring every label is perfectly correct.

import openai
import numpy as np
from sklearn.metrics.pairwise import cosine_similarity

client = openai.OpenAI()

POOL = [{"input": "Stunning visuals and a powerful emotional score.", "label": "Positive"},
        {"input": "The plot drags and all characters feel underwritten.", "label": "Negative"},
        {"input": "A joyful, heartwarming film I would happily rewatch.", "label": "Positive"},
        {"input": "Overly long with significant plot holes.", "label": "Negative"},
        {"input": "Brilliant script, tight direction, career-best performance.", "label": "Positive"},
        {"input": "Tedious from the opening scene to the closing credits.", "label": "Negative"}]

def embed(texts):
    resp = client.embeddings.create(input=texts, model="text-embedding-3-small")
    return np.array([d.embedding for d in resp.data])

def retrieve_examples(query, pool, k=4):
    q_emb = embed([query])
    p_emb = embed([ex["input"] for ex in pool])
    sims  = cosine_similarity(q_emb, p_emb)[0]
    top_k = np.argsort(sims)[::-1][:k]
    return [pool[i] for i in top_k]

QUERY = "The cinematography was beautiful but the pacing felt sluggish."
retrieved = retrieve_examples(QUERY, POOL, k=3)
random_ex = [POOL[i] for i in np.random.choice(len(POOL), 3, replace=False)]
print("Retrieved:", [e["label"] for e in retrieved])
print("Random:   ", [e["label"] for e in random_ex])

Retrieval-based example selection consistently outperforms random selection by 3–8% accuracy on classification tasks, and the gap widens on tasks with high label diversity or complex input distributions. The intuition is straightforward: semantically similar demonstrations teach the model how to handle inputs similar to the test case, while random demonstrations may introduce irrelevant distribution shift. The cost is an embedding API call for each new test input — typically 1–2 ms and a fraction of a cent. For latency-sensitive applications, pre-computing embeddings for all pool examples and building a cached nearest-neighbour index (FAISS, Qdrant, Chroma) amortises this cost to a single vector search at inference time.

Example Selection Strategies

Example selection is one of the highest-leverage design decisions in few-shot prompting. The choice of which k demonstrations to include from a pool of candidates can swing accuracy by 10–20% on challenging tasks with diverse input distributions. Four main strategies are used in practice. Random selection is simple and fast but yields high variance; it is the baseline but rarely the best choice. Retrieval-based selection embeds the query and retrieves the k nearest pool examples by cosine similarity; this is typically the strongest performer for heterogeneous input distributions. Diversity-based selection uses k-means clustering or maximum marginal relevance to maximise coverage of the example space, preventing redundant demonstrations that all illustrate the same input pattern. Influence-function selection scores each candidate example by its estimated contribution to reducing the model's loss on the target input; theoretically principled but computationally expensive. For most production use cases, retrieval-based selection with a small embedding model is the best trade-off of performance and inference cost.

  • Random selection: O(1) query time, high variance, useful only when pool is small and homogeneous
  • Retrieval-based (kNN): embed query + pool, cosine similarity ranking — best average accuracy for diverse pools
  • Diversity-based (k-means or MMR): cluster pool and select one example per cluster — reduces redundancy across shots
  • BM25 lexical retrieval: fast term-overlap ranking with no embedding API call — good for very large pools (10K+ examples)
  • Influence selection: estimate per-example gradient contribution — most accurate but expensive; use offline for static prompts
  • Coverage + quality filter: retrieve 2k candidates by similarity, re-rank by label balance and format diversity, keep top k

Format and Order Sensitivity

Few-shot prompting is far more sensitive to the ordering and formatting of examples than practitioners typically expect. Lu et al. (2022, "Fantastically Ordered Prompts") showed that accuracy on 8-shot sentiment classification varies by as much as ±15 percentage points depending solely on the order in which the 8 examples appear in the prompt — with the same model, same examples, and same test inputs. The recency bias is the primary driver: the model assigns higher weight to examples appearing near the end of the prompt (just before the test input). If the last 2–3 examples all carry the same label, the model tends to predict that label regardless of the test input. Format choices also matter: providing the label as a continuation of the input line vs on a separate line, using "Label:" vs no prefix, and including or omitting example separators all affect accuracy by 2–7%. The recommended practice is to (a) balance labels across the full example sequence, (b) ensure label diversity among the final 3 positions, and (c) evaluate across multiple orderings before settling on a fixed prompt.

import openai
import random
import statistics

client = openai.OpenAI()

SYSTEM = "Classify sentiment as Positive or Negative. Reply with one word."
EXAMPLES = [("Fantastic performances all round.", "Positive"),
            ("I fell asleep halfway through.", "Negative"),
            ("A breathtaking visual spectacle.", "Positive"),
            ("The script was painfully weak.", "Negative")]
TARGET = "The direction was inspired but the overall pacing dragged."

def classify_ordered(examples, text):
    msgs = [{"role": "system", "content": SYSTEM}]
    for inp, lbl in examples:
        msgs += [{"role": "user", "content": inp}, {"role": "assistant", "content": lbl}]
    msgs.append({"role": "user", "content": text})
    resp = client.chat.completions.create(model="gpt-4o-mini", messages=msgs, max_tokens=4)
    return resp.choices[0].message.content.strip()

predictions = []
for trial in range(10):
    shuffled = EXAMPLES.copy()
    random.shuffle(shuffled)
    pred = classify_ordered(shuffled, TARGET)
    predictions.append(pred)
    print(f"Trial {trial+1:2d}: last_label={shuffled[-1][1]:8s}  pred={pred}")
print(f"\nPositive rate across 10 orderings: {predictions.count('Positive')}/10")

The order sensitivity experiment reveals a critical practical insight: never report few-shot accuracy from a single prompt ordering. The variance across 10 random orderings can span ±15% absolute accuracy for the same model and examples. To get a reliable estimate, run the same evaluation across 5–10 orderings and report the mean ± standard deviation. For production deployment, fix a well-evaluated ordering rather than randomising at inference time, since consistent ordering allows reproducible evaluation and avoids worst-case orderings appearing in production traffic.

Label Calibration

Even with no few-shot examples, LLMs have strong prior biases toward certain labels — a form of distributional shift inherited from pretraining. A model trained predominantly on positive product reviews will assign higher prior probability to "Positive" than "Negative" regardless of the input. Zhao et al. (2021, "Calibrate Before Use") proposed contextual calibration to correct for this bias. The method estimates P(y | content-free input) — the model's output distribution when given a semantically null input such as "N/A" or an empty string — as a proxy for the label prior. At inference time, the raw logits are divided by these prior probabilities to produce calibrated predictions. Calibrated few-shot prompting consistently outperforms uncalibrated prompting by 3–10% on classification tasks, especially when the training-set label distribution differs from the task's test distribution. The technique requires only a few API calls to estimate the prior and adds negligible overhead at inference time.

import openai
import numpy as np

client = openai.OpenAI()
LABELS = ["Positive", "Negative"]
SYSTEM = "Classify sentiment. Reply with one word: Positive or Negative."

def get_label_logprobs(text, examples):
    """Return approximate probability of each label token via top_logprobs."""
    msgs = [{"role": "system", "content": SYSTEM}]
    for inp, lbl in examples:
        msgs += [{"role": "user", "content": inp}, {"role": "assistant", "content": lbl}]
    msgs.append({"role": "user", "content": text})
    resp = client.chat.completions.create(
        model="gpt-4o-mini", messages=msgs, max_tokens=2,
        logprobs=True, top_logprobs=5
    )
    top = {t.token: np.exp(t.logprob)
           for t in resp.choices[0].logprobs.content[0].top_logprobs}
    return {lbl: top.get(lbl, 1e-9) for lbl in LABELS}

def calibrated_predict(text, examples):
    prior  = get_label_logprobs("N/A", [])   # content-free prior
    probs  = get_label_logprobs(text, examples)
    calibr = {lbl: probs[lbl] / prior[lbl] for lbl in LABELS}
    pred   = max(calibr, key=calibr.get)
    print(f"raw={probs}  calibrated={calibr}  pred={pred}")
    return pred

calibrated_predict("A decent film — nothing special.", [])

Limits of ICL

In-context learning has fundamental limitations that motivate more powerful prompting techniques. First, ICL does not perform well on tasks requiring precise numerical computation or multi-step logical reasoning — the model produces an answer in a single forward pass without the ability to verify or revise intermediate steps. Second, the number of shots is bounded by the context window size; at 16 shots with long examples, the prompt may consume thousands of tokens, crowding out the actual task input. Third, ICL accuracy on truly novel tasks (tasks unlike anything in pretraining) saturates at a much lower ceiling than fine-tuning — the model can adjust its output format but cannot learn genuinely new skills from a handful of examples. Fourth, the random-label robustness result (accuracy degrades by only 5–15% when all demonstration labels are randomised) suggests that models are partly pattern-matching to format rather than learning the semantic mapping, which limits maximum accuracy on tasks requiring deep understanding. Chain-of-thought prompting, introduced by Wei et al. (2022), addresses the reasoning limitation by eliciting explicit step-by-step intermediate reasoning before the final answer.

  • Context window cap: 16 shots with long examples can consume 4K+ tokens, reducing usable input length
  • Multi-step arithmetic and symbolic reasoning fails without explicit reasoning steps — chain-of-thought is required
  • Truly novel tasks with no pretraining overlap cannot be learned from k examples alone; fine-tuning is necessary
  • Label correctness matters less than format — randomising labels only degrades accuracy by 5–15% on many tasks
  • Recency bias: the last 2–3 demonstrations disproportionately influence predictions regardless of their relevance
  • No self-correction mechanism: errors compound silently without explicit reasoning traces to audit

Key Takeaways

Zero-shot and few-shot prompting are the first tools to reach for when working with LLMs on a new task. Zero-shot works well for instruction-tuned models on clearly described, standard tasks and requires no labelled data. Few-shot prompting consistently improves accuracy by providing format anchors and shifting the output distribution toward the task, but performance is sensitive to example selection, ordering, and label balance. Retrieval-based example selection outperforms random selection, especially for heterogeneous task distributions. Label calibration removes systematic prior bias and adds 3–10% accuracy with minimal cost. For tasks requiring multi-step reasoning, few-shot ICL provides the format scaffold but chain-of-thought prompting is needed to elicit the intermediate reasoning steps that enable correct answers.

  • Start with zero-shot using an explicit system prompt — instruction-tuned models often need no examples for standard tasks
  • Use 4-shot as the default; diminishing returns beyond 4 examples on most classification and extraction tasks
  • Select examples via cosine similarity of embeddings (retrieval-based) rather than random selection
  • Evaluate across at least 5 example orderings; report mean accuracy not single-run accuracy
  • Balance labels in demonstrations — equal counts per class prevent recency-bias skew toward any single label
  • Apply label calibration (divide by P(y|N/A)) when you suspect systematic bias toward a majority output label
  • For reasoning tasks, transition from plain few-shot ICL to chain-of-thought prompting to unlock multi-step accuracy
