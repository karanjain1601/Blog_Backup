RAG Evaluation: Retrieval and Generation Metrics

Retrieval-Augmented Generation (RAG) pipelines consist of two distinct stages — retrieval and generation — each of which can fail independently. A pipeline with excellent retrieval can still produce hallucinated answers; a faithful generator is useless if it receives irrelevant context. Evaluating RAG therefore requires separate metric families for each stage, plus end-to-end metrics that capture the combined system behaviour. This note covers the full evaluation stack: offline retrieval metrics (Recall@k, MRR, NDCG), generation quality metrics (faithfulness, answer relevancy, context precision and recall), automated evaluation frameworks (RAGAS and TruLens), human evaluation strategies, and a practical guide to building a regression test suite.

Overview

RAG evaluation can be decomposed into three layers. The first layer is retrieval quality: given a query, does the retriever surface the documents that contain the answer? Retrieval metrics are computed offline against a labelled dataset of (query, relevant_document_ids) pairs and require no LLM calls — they are fast and cheap. The second layer is generation quality: given retrieved context, does the generator produce an answer that is faithful to the context, relevant to the question, and correct? Generation metrics typically require either ground-truth answers or LLM-based judges. The third layer is end-to-end correctness: does the final answer match the reference answer by exact match or F1? RAGAS and TruLens provide integrated frameworks that compute all three layers in a single evaluation run. Building a regression suite means running these metrics automatically on every system change and failing the build when scores drop below defined thresholds.

Retrieval Quality Metrics

Retrieval metrics measure how well the retriever ranks relevant documents. Recall@k asks: of all relevant documents, what fraction appear in the top-k results? MRR@k (Mean Reciprocal Rank) asks: where does the first relevant document appear, on average? NDCG@k (Normalized Discounted Cumulative Gain) generalises MRR by rewarding relevant documents that appear earlier in the ranking and handling graded relevance. All three are computed per query and averaged over a test set. They require a labelled retrieval dataset with known relevant documents per query, but no LLM calls — making them the cheapest evaluation signal in the RAG stack. Typical targets: Recall@5 > 0.85, MRR@10 > 0.75, NDCG@10 > 0.80 for a well-tuned retriever.

import numpy as np
from typing import List, Dict

def recall_at_k(retrieved: List[str], relevant: List[str], k: int) -> float:
    """Fraction of relevant docs found in top-k retrieved results."""
    top_k = set(retrieved[:k])
    rel   = set(relevant)
    return len(top_k & rel) / max(len(rel), 1)

def mrr_at_k(retrieved: List[str], relevant: List[str], k: int) -> float:
    """Reciprocal rank of the first relevant doc in top-k results."""
    rel = set(relevant)
    for rank, doc_id in enumerate(retrieved[:k], start=1):
        if doc_id in rel:
            return 1.0 / rank
    return 0.0

def ndcg_at_k(retrieved: List[str], relevant: List[str], k: int) -> float:
    """Normalised discounted cumulative gain at k (binary relevance)."""
    rel = set(relevant)
    dcg  = sum(1.0 / np.log2(r + 2) for r, d in enumerate(retrieved[:k]) if d in rel)
    idcg = sum(1.0 / np.log2(r + 2) for r in range(min(len(rel), k)))
    return dcg / idcg if idcg > 0 else 0.0

def evaluate_retrieval(
        queries: List[str],
        retrieved_docs: List[List[str]],
        relevant_docs: List[List[str]],
        ks: List[int] = [1, 5, 10]) -> Dict[str, float]:
    """Compute Recall@k, MRR@k, NDCG@k averaged over all queries."""
    results = {}
    for k in ks:
        results[f"recall@{k}"]  = np.mean([recall_at_k(r, g, k) for r, g in zip(retrieved_docs, relevant_docs)])
        results[f"mrr@{k}"]     = np.mean([mrr_at_k(r, g, k)    for r, g in zip(retrieved_docs, relevant_docs)])
        results[f"ndcg@{k}"]    = np.mean([ndcg_at_k(r, g, k)   for r, g in zip(retrieved_docs, relevant_docs)])
    for metric, score in results.items():
        print(f"{metric:<12} = {score:.4f}")
    return results

Retrieval metrics have an important limitation: they only measure whether relevant documents are retrieved, not whether the generator uses them correctly. A system can achieve Recall@5=0.95 while still generating unfaithful answers if the generator ignores the retrieved context or over-generates beyond it. This is why generation metrics are equally important and must always be measured alongside retrieval metrics — never treat a high retrieval score as a proxy for overall RAG quality.

Generation Quality Metrics

Generation metrics assess the quality of the answer produced by the LLM given retrieved context. Faithfulness measures whether every claim in the generated answer is supported by the retrieved context — it catches hallucination. Answer relevancy measures whether the answer actually addresses the question — it catches vague or off-topic responses. Context precision measures whether the retrieved context is actually used (penalises irrelevant context that dilutes signal). Context recall measures whether all information in the ground-truth answer is present in the retrieved context (penalises incomplete retrieval that prevents correct answering). Exact match (EM) and F1 token overlap compare the answer directly to a reference answer and are best used when ground truth is available. LLM-based metrics (faithfulness, relevancy) do not require ground-truth answers but require LLM inference budget for the judge model.

import re
import json
from typing import List
from openai import OpenAI

client = OpenAI()  # requires OPENAI_API_KEY env var

FAITHFULNESS_PROMPT = """You are a fact-checker. Given a context and a list of claims,
decide for each claim whether it is fully supported by the context.
Output a JSON list of booleans, one per claim.

Context: {context}

Claims: {claims_json}

Output only the JSON list, e.g. [true, false, true]."""

def extract_claims(answer: str) -> List[str]:
    """Split answer into individual sentences as atomic claims."""
    return [s.strip() for s in re.split(r'(?<=[.!?])\s+', answer) if len(s.strip()) > 10]

def score_faithfulness(context: str, answer: str, model: str = "gpt-4o-mini") -> float:
    """LLM-based faithfulness: fraction of answer claims supported by context."""
    claims = extract_claims(answer)
    if not claims:
        return 1.0
    prompt = FAITHFULNESS_PROMPT.format(
        context=context[:3000],
        claims_json=json.dumps(claims)
    )
    response = client.chat.completions.create(
        model=model,
        messages=[{"role": "user", "content": prompt}],
        temperature=0
    )
    raw = response.choices[0].message.content.strip()
    try:
        verdicts = json.loads(raw)
        supported = sum(1 for v in verdicts if v is True)
        score = supported / len(verdicts)
    except (json.JSONDecodeError, TypeError):
        score = 0.0
    print(f"Faithfulness: {score:.3f}  ({sum(1 for v in verdicts if v is True)}/{len(verdicts)} claims supported)")
    return score

RAGAS Framework

RAGAS (Retrieval Augmented Generation Assessment) is an open-source Python library that provides a standardised, automated evaluation pipeline for RAG systems. It implements faithfulness, answer relevancy, context precision, and context recall as LLM-based metrics and wraps them in a single evaluate() call. RAGAS expects a HuggingFace Dataset with columns: question, answer (generated), contexts (list of retrieved passages), and optionally ground_truth (reference answer for context recall). Each metric is computed by prompting a configurable judge LLM (default: OpenAI gpt-4o) and averaging across the dataset. RAGAS is the de-facto evaluation standard for RAG systems as of 2024–2025 and is widely used in production pipelines.

RAGAS metrics are computed per row and averaged. The library also provides TestsetGenerator for synthetically creating evaluation datasets from a document corpus — it generates question-answer pairs with positive context windows, enabling evaluation without manually labelled data. However, synthetic datasets can miss the distribution of real user questions. For production use, mix 20–30% synthetic questions with 70–80% sampled real queries. RAGAS scores above 0.85 for faithfulness and 0.80 for answer relevancy are considered strong for most RAG applications.

TruLens Triad

TruLens (from TruEra) is an alternative evaluation framework that defines the RAG Triad: answer relevance, context relevance, and groundedness. Answer relevance checks whether the generated answer is relevant to the input question. Context relevance checks whether each retrieved chunk is relevant to the question — penalising over-retrieval of noise. Groundedness is equivalent to RAGAS faithfulness: does the answer follow from the retrieved context? TruLens instruments the RAG application via wrappers (TruChain for LangChain, TruLlama for LlamaIndex) that automatically capture every retrieval and generation event at runtime, then compute the Triad metrics on a dashboard. This makes TruLens especially useful for continuous monitoring of live RAG systems, not just offline evaluation.

Retrieval Recall and Faithfulness Are Uncorrelated: Retrieval recall and generation faithfulness can be uncorrelated — a system with excellent retrieval (recall@5=0.9) can still produce unfaithful answers by ignoring retrieved context; always measure both components independently. High recall guarantees relevant documents are available to the generator, but not that the generator will use them faithfully. Conversely, a faithfulness score of 1.0 means every claim is grounded in context, but if that context was wrong or irrelevant, the answer is still incorrect. Measure all four RAGAS metrics together and treat any single metric in isolation as insufficient.

Human Evaluation vs Automated

Human evaluation remains the gold standard for RAG quality assessment. Annotators rate answers on dimensions including: correctness (does the answer match the factual truth?), completeness (does it cover all relevant aspects?), faithfulness (is every claim supported by the context shown?), and fluency (is the language natural?). Human evaluation is expensive (typically $2–10 per question for expert annotators) and slow (days to weeks for a large test set). Automated metrics using LLM judges correlate reasonably well with human judgements: GPT-4-based faithfulness achieves 0.85–0.90 Pearson correlation with human faithfulness ratings in controlled studies. The recommended practice is to run automated metrics continuously and do a human evaluation audit quarterly or after major system changes to calibrate whether automated scores still track human satisfaction.

  • Human evaluation is the calibration anchor — run it quarterly to validate that automated metrics still correlate
  • LLM-as-judge (GPT-4o) achieves 0.85–0.90 correlation with human faithfulness ratings
  • LLM judges have positional bias (prefer first-listed answers) and verbosity bias (prefer longer answers) — mitigate with randomised ordering and length controls
  • RAGAS synthetic testsets are cheap to generate but miss real user query distributions
  • Mix 20–30% synthetic questions with 70–80% sampled real queries for a representative eval set
  • Always evaluate at the query-level (per-row scores) not just aggregate means — bimodal score distributions hide failure modes

Building an Eval Suite

A production RAG eval suite is a set of golden question-answer pairs that runs automatically after every system change (retriever update, prompt change, model upgrade) and asserts that quality metrics do not degrade. The suite should contain 50–200 questions representative of real usage, cover edge cases (ambiguous questions, multi-hop reasoning, questions with no answer in the corpus), and define explicit pass/fail thresholds. Evaluation is gated in CI: if faithfulness drops below 0.85 or answer relevancy below 0.80 relative to the baseline run, the pipeline fails and the change is blocked. This prevents silent regressions — the most common failure mode when iterating on RAG components.

        rows.append({"question": item["question"], "answer": out["answer"],

        print(f"  {status}  {metric:<22} {score:.3f}  (threshold >= {threshold})")
        if score < threshold:
            passed = False
    if not passed:
        print("\nREGRESSION DETECTED — blocking deployment")
        sys.exit(1)
    print("\nAll metrics passed.")
    return True

Key Takeaways

RAG evaluation requires measuring both retrieval and generation stages independently. Retrieval metrics (Recall@k, MRR@k, NDCG@k) are fast and cheap but only measure document ranking, not answer quality. Generation metrics (faithfulness, answer relevancy, context precision, context recall) require LLM inference but directly measure what users care about. RAGAS provides the industry-standard implementation of generation metrics; TruLens is better suited for live monitoring. A production eval suite should combine 50–200 golden questions with automated threshold enforcement in CI, preventing silent regressions when any component of the RAG pipeline changes.

  • Always measure retrieval and generation metrics separately — high retrieval recall does not guarantee faithful generation
  • RAGAS evaluate() computes all four generation metrics in a single pass over a HuggingFace Dataset
  • Use faithfulness > 0.85 and answer_relevancy > 0.80 as minimum deployment thresholds
  • LLM-as-judge metrics correlate 0.85–0.90 with human judgement for faithfulness
  • Run a regression suite in CI after every system change and fail the build on score degradation
  • Calibrate automated metrics against human evaluation quarterly to detect metric drift
