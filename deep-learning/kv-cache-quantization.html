KV Cache Quantization

During autoregressive decoding, a transformer reuses the attention keys and values computed for all previous tokens. Storing these tensors — the KV cache — avoids redundant recomputation at each generation step. The cost, however, is memory: for long sequences or large batches, the KV cache can easily rival or exceed the size of the model weights themselves. KV cache quantization compresses these stored tensors from FP16 or BF16 to INT8, FP8, or even INT4, cutting memory pressure by 2–4x and enabling larger batches, longer context windows, or both — without retraining the model and without changing the decoding algorithm.

Overview

KV cache quantization sits at the boundary between model quantization and inference system design. Unlike weight quantization, which is a one-time offline step, KV cache quantization happens at runtime: tensors are quantized just before being written to the cache store, and dequantized just before being read back for attention computation. This online nature introduces two key constraints. First, the quantization must be fast enough not to dominate the attention kernel time — ideally, quantize/dequantize is fused into the attention kernel itself. Second, the error introduced accumulates token by token over the generation sequence; a small per-token error can compound into noticeable degradation for coherence-critical long-context tasks. The key design decisions are: choice of numeric format (INT8, FP8, INT4), granularity of the scale factor (per-tensor, per-token, or per-head), and whether to apply fine-grained residual correction schemes such as KVQuant.

  • KV cache is the dominant memory consumer at long context: for Llama-3-8B at seq=32K, batch=8, FP16 KV cache uses ~137 GB — dwarfing the ~13 GB of model weights.
  • Quantization to INT8 or FP8 halves the KV memory footprint with typically <0.5% relative attention output error on Gaussian activations.
  • Scale granularity matters: per-head scales outperform per-tensor for models with activation outliers concentrated in specific heads.
  • FP8 (E4M3 or E5M2) preserves dynamic range better than INT8 for attention keys, which can exhibit large magnitude variation across heads.
  • KVQuant and NF4-KV apply non-uniform quantization grids tuned to the observed distribution of cached keys and values.
  • vLLM supports fp8 and int8 KV cache dtypes via the kv_cache_dtype parameter, with automatic scale management per layer and head.

KV Cache Memory Anatomy

The KV cache for a single transformer layer stores two tensors — K and V — each of shape (batch_size, n_heads, seq_len, head_dim). Across all layers the total memory is: 2 × n_layers × n_heads × seq_len × head_dim × batch_size × bytes_per_element. For Llama-3-8B (32 layers, 32 heads, head_dim=128) in FP16 (2 bytes), a single sequence at 32K context uses 2 × 32 × 32 × 32768 × 128 × 2 = 17.18 GB — already exceeding the model weights at a single batch element. Scaling to batch size 8 brings this to 137 GB. Quantizing to INT8 (1 byte) halves these figures; FP8 gives the same halving; INT4 (0.5 bytes) achieves a 4x reduction. The following code computes this across all dtype options and sequence lengths.

from dataclasses import dataclass
from typing import List

@dataclass
class LlamaKVConfig:
    n_layers: int = 32
    n_heads: int = 32
    head_dim: int = 128  # Llama-3-8B (GQA-free approximation)

def kv_cache_bytes(cfg, batch, seq, dtype_bytes):
    # Total KV cache: 2(K+V) x layers x heads x seq x head_dim x element_bytes
    return int(2 * cfg.n_layers * cfg.n_heads * seq * cfg.head_dim * dtype_bytes * batch)

cfg = LlamaKVConfig()
hidden = cfg.n_heads * cfg.head_dim            # 4096
w_gb = 12 * hidden**2 * cfg.n_layers * 2 / 1e9  # approx FP16 weight size ~12.9 GB
print('Llama-3-8B weights (FP16): %.2f GB' % w_gb)

dtypes = [('FP16', 2.0), ('BF16', 2.0), ('FP8', 1.0), ('INT8', 1.0), ('INT4', 0.5)]
seqs = [8192, 32768, 131072]
print('\n%-10s %5s | %8s %9s %10s  (batch=1, GB)' % ('KV dtype', 'bytes', 'seq=8K', 'seq=32K', 'seq=128K'))
print('-' * 60)
for label, db in dtypes:
    vals = [kv_cache_bytes(cfg, 1, s, db) / 1e9 for s in seqs]
    print('%-10s %5.1f | %8.3f %9.3f %10.3f' % (label, db, vals[0], vals[1], vals[2]))

print('\nBatch=8, seq=32K vs model weights:')
for label, db in dtypes:
    kv_gb = kv_cache_bytes(cfg, 8, 32768, db) / 1e9
    tag = 'EXCEEDS WEIGHTS' if kv_gb > w_gb else '%.2fx weights' % (kv_gb / w_gb)
    print('  %-6s %.2f GB  -- %s' % (label, kv_gb, tag))

Running the above reveals that FP16 KV cache at batch=8, seq=32K (137 GB) exceeds model weights by more than 10x, while INT8 KV (68 GB) still far exceeds weights but brings the footprint within range of a two-GPU setup. At seq=128K, even INT8 KV at batch=1 requires 68 GB — a GPU cluster requirement. INT4 KV at seq=128K, batch=1 costs 34 GB, approaching practical single-node territory. This arithmetic explains why KV cache quantization is the single most impactful optimization for long-context serving: no amount of weight quantization addresses the KV growth with sequence length.

INT8 KV Cache

INT8 KV quantization maps each floating-point element of K and V to a signed 8-bit integer in [-128, 127] using a linear scale. The most common granularity is per-token symmetric quantization: for each token position t in a given head, the scale is max(|K[t, :]|) / 127, computed over the head_dim dimension. This produces one scale value per (batch, head, token) triplet, stored alongside the quantized cache. At attention time, the INT8 cache is dequantized back to FP16 before the scaled dot-product computation. Fused CUDA kernels (as in FlashAttention-2 with INT8 KV support) fold the dequantization into the attention kernel to avoid materializing the FP16 tensor, but the unfused implementation below is instructive for understanding the error introduced.

import torch
import torch.nn.functional as F
from typing import Tuple

def quantize_kv_sym_int8(x: torch.Tensor) -> Tuple[torch.Tensor, torch.Tensor]:
    '''
    Symmetric per-token INT8 quantization of a KV tensor.
    x: (batch, n_heads, seq_len, head_dim) in FP16 or BF16.
    Returns: (int8 tensor, per-token scale of shape (batch, n_heads, seq_len, 1)).
    '''
    amax = x.float().abs().amax(dim=-1, keepdim=True).clamp(min=1e-8)
    scale = amax / 127.0
    x_int8 = (x.float() / scale).round().clamp(-128, 127).to(torch.int8)
    return x_int8, scale

def dequantize_kv_int8(x_int8: torch.Tensor, scale: torch.Tensor) -> torch.Tensor:
    '''Dequantize cached INT8 KV tensor back to FP16 before attention.'''
    return x_int8.to(torch.float16) * scale.to(torch.float16)

# Measure attention output error: INT8 KV vs FP16 reference
torch.manual_seed(0)
B, H, T, D = 1, 32, 2048, 128
q = torch.randn(B, H, T, D, dtype=torch.float16)
k = torch.randn(B, H, T, D, dtype=torch.float16)
v = torch.randn(B, H, T, D, dtype=torch.float16)

ref_out = F.scaled_dot_product_attention(q, k, v)

# Simulate cache store (quantize) then load (dequantize)
k_q, k_s = quantize_kv_sym_int8(k)
v_q, v_s = quantize_kv_sym_int8(v)
k_dq = dequantize_kv_int8(k_q, k_s)
v_dq = dequantize_kv_int8(v_q, v_s)
int8_out = F.scaled_dot_product_attention(q, k_dq, v_dq)

err = (int8_out - ref_out).abs()
print('Attention output error (INT8 KV vs FP16 reference):')
print('  max  absolute: %.6f' % err.max().item())
print('  mean absolute: %.7f' % err.mean().item())
print('  relative err:  %.4f%%' % ((err.mean() / ref_out.abs().mean()).item() * 100))
kv_fp16_mb = 2 * B * H * T * D * 2 / 1e6
kv_int8_mb = 2 * B * H * T * D * 1 / 1e6
print('  KV memory: %.1f MB (FP16) vs %.1f MB (INT8) -- 2x saving' % (kv_fp16_mb, kv_int8_mb))

On typical Gaussian attention keys and values the per-token INT8 scheme introduces a relative attention output error of roughly 0.01–0.05%. This is well within the noise floor for most generation tasks. The error grows for activations with heavy-tailed distributions — in practice, later layers and query-heavy attention heads can exhibit larger K magnitudes, increasing quantization error. Monitoring the distribution of cached K values per head during profiling is the recommended way to identify heads where INT8 may be insufficient.

FP8 KV Cache

FP8 quantization encodes floating-point values using 8 bits with an explicit exponent field, offering better dynamic range than INT8 at the same storage cost. NVIDIA's H100 and AMD's MI300X natively support FP8 arithmetic. Two FP8 formats are in common use for KV cache: E4M3 (4-bit exponent, 3-bit mantissa, range ±448) and E5M2 (5-bit exponent, 2-bit mantissa, range ±57344). E4M3 is preferred for KV cache because it offers higher precision (more mantissa bits) at the cost of slightly narrower range; attention keys rarely exceed ±448 after RoPE embedding. FP8 KV cache requires a per-tensor or per-head scale factor — unlike INT8, the hardware FP8 format is self-normalising within its range, so calibration establishes a single amax scale to map the FP16 activation range into the FP8 representable range. vLLM implements FP8 KV cache using E4M3 with per-tensor static scales derived from calibration data.

  • E4M3 FP8: range ±448, 3 mantissa bits — preferred for KV cache precision; used by vLLM and TensorRT-LLM.
  • E5M2 FP8: range ±57344, 2 mantissa bits — better for weights with larger dynamic range; less suited to KV cache.
  • FP8 hardware support: H100 (fp8 tensor cores), MI300X (fp8 matmul), upcoming consumer GPUs; on older hardware FP8 is emulated via FP16.
  • Scale management: FP8 KV requires one amax scale per head (or per tensor) stored at FP32; this scale overhead is negligible (32 × 32 float32 = 4 KB for Llama-3-8B).
  • Numerical equivalence: E4M3 FP8 with per-head scaling achieves attention output error comparable to INT8 per-token for standard transformer attention patterns.
  • vLLM kv_cache_dtype='fp8': enables FP8 KV across all layers using static per-tensor scales loaded from a calibration JSON file or defaulting to 1.0.

Per-head vs Per-token Scaling

The granularity of the scale factor profoundly affects quantization quality. Per-tensor scaling uses a single scale for the entire K or V cache — simple but sensitive to outlier heads or tokens. Per-token scaling (one scale per token position per head) adapts to local magnitude variation and is the standard for INT8. Per-head scaling (one scale per attention head, fixed across tokens) is the natural fit for FP8, since it matches the static calibration workflow and avoids per-token scale storage. Per-head scaling becomes especially important when different attention heads exhibit dramatically different activation magnitudes — a known property of large LLMs where certain heads specialize in high-magnitude pattern detection. The following code quantifies the error difference between per-tensor and per-head scaling when one head has strong outlier activations.

import torch
from typing import Tuple

def per_head_scales_from_calib(
    calib_keys: torch.Tensor,
    bits: int = 8
) -> torch.Tensor:
    '''
    Compute per-head INT8 scale from calibration data.
    calib_keys: (n_samples, n_heads, seq_len, head_dim).
    Returns scale tensor of shape (n_heads,).
    '''
    amax = calib_keys.float().abs().amax(dim=(0, 2, 3))  # (n_heads,)
    return amax / (2 ** (bits - 1) - 1)

def quantize_per_head(x: torch.Tensor, scales: torch.Tensor, bits: int = 8) -> torch.Tensor:
    '''x: (B, H, T, D), scales: (H,) -> returns int8 tensor.'''
    s = scales.view(1, -1, 1, 1)
    return (x.float() / s).round().clamp(-128, 127).to(torch.int8)

torch.manual_seed(42)
n_calib, H, T, D = 4, 32, 512, 128
calib_k = torch.randn(n_calib, H, T, D, dtype=torch.float16)
calib_k[:, 0, :, :] *= 20.0   # head 0 has strong outlier activations
calib_k[:, 7, :, :] *= 8.0    # head 7 has moderate outliers

# Calibration: per-head vs per-tensor
ph_scales = per_head_scales_from_calib(calib_k)           # (H,)
pt_scale  = calib_k.float().abs().max() / 127.0           # scalar

# Evaluate on one calibration example
test_k = calib_k[0]   # (H, T, D)
# Per-tensor
kq_pt  = (test_k.float() / pt_scale).round().clamp(-128, 127).to(torch.int8)
kdq_pt = kq_pt.to(torch.float16) * pt_scale.to(torch.float16)
# Per-head
kq_ph  = quantize_per_head(test_k.unsqueeze(0), ph_scales).squeeze(0)
kdq_ph = kq_ph.to(torch.float16) * ph_scales.view(-1, 1, 1).to(torch.float16)

print('Head  | per-tensor MAE | per-head MAE | improvement')
print('-' * 52)
for h in [0, 1, 7, 15, 31]:
    err_pt = (kdq_pt[h] - test_k[h]).abs().mean().item()
    err_ph = (kdq_ph[h] - test_k[h]).abs().mean().item()
    imp = (1 - err_ph / max(err_pt, 1e-9)) * 100
    print('  %2d  |   %.5f      |   %.5f    | %+.1f%%' % (h, err_pt, err_ph, imp))

The output shows that for heads with outlier activations (heads 0 and 7 in the demo), per-head scaling reduces mean absolute error by 60–90% relative to per-tensor scaling. For non-outlier heads, the difference is negligible. This explains the empirical finding in several KV cache quantization papers: per-tensor scaling delivers acceptable quality on small models where activations are well-behaved, but per-head (or per-token) scaling is essential for models above ~7B parameters where inter-head magnitude variation increases substantially.

KVQuant and Fine-grained Methods

KVQuant (Hooper et al., 2024) pushes KV quantization below INT8 by applying three complementary techniques. First, pre-RoPE key quantization: quantizing keys before rotary position embedding is applied, rather than after, significantly reduces activation range because RoPE introduces position-dependent rotation that spreads key magnitudes. Second, non-uniform quantization grids: rather than a uniform integer grid, KVQuant fits a per-channel quantization lookup table calibrated on the observed distribution of key and value activations — analogous to NF4 (Normal Float 4) for weights, but applied per head to cached activations. Third, per-channel attention sink handling: the first few tokens in a sequence (attention sinks) receive abnormally high attention scores; KVQuant keeps these tokens in FP16 while quantizing the rest. Together these allow KVQuant to achieve 3-bit average KV precision with perplexity close to FP16 — roughly equivalent to halving the 2x saving of INT8 to a 5x saving over FP16.

  • Pre-RoPE quantization (KVQuant): quantize keys before applying rotary embeddings to reduce dynamic range; requires modifying the attention kernel to apply RoPE on dequantized keys.
  • Non-uniform grids (NF4-KV): calibrate a per-head lookup table matching the empirical key/value distribution; gives better precision at tails than uniform INT4.
  • Attention sink preservation: keep the first 4–8 sink tokens in FP16 within the quantized cache; these tokens attract disproportionate attention and quantization error on them propagates strongly.
  • KIVI (Liu et al., 2024): uses a grouped INT2 scheme for keys with a small FP16 residual per group; achieves ~2-bit average with competitive accuracy on short to medium contexts.
  • FlexGen KV cache: off-loads INT8 KV to CPU or NVMe with asynchronous prefetch, trading latency for memory capacity in throughput-oriented serving.
  • Cascading granularity: use INT8 for recent tokens (where attention is high) and INT4 or INT2 for distant tokens (where attention is sparse) — adapts to attention recency bias.

Integration with vLLM

vLLM exposes KV cache quantization through the kv_cache_dtype parameter of the LLM class. Setting kv_cache_dtype='fp8' enables E4M3 FP8 KV storage across all layers using a static per-tensor scale. The scale can be provided via a quantization parameter file (a JSON mapping layer names to scale tensors) produced by running vLLM's offline calibration script on a representative dataset. Without a scale file, vLLM defaults to scale=1.0, which is acceptable for FP8 because the E4M3 range (±448) comfortably covers typical attention key magnitudes without saturation. Setting kv_cache_dtype='int8' applies per-token symmetric INT8. The following code benchmarks FP8 KV against BF16 KV on a small prompt set, reporting throughput and peak GPU memory.

from vllm import LLM, SamplingParams
import time
import torch

prompts = [
    'Describe how transformer attention works in two sentences.',
    'What are the tradeoffs between INT8 and FP8 KV cache quantization?',
    'Explain why KV cache memory grows linearly with sequence length.',
    'List three techniques for reducing KV cache memory in LLM serving.',
]
sampling = SamplingParams(temperature=0.0, max_tokens=120)

results = {}
for kv_dtype in ['auto', 'fp8']:
    label = 'BF16 KV' if kv_dtype == 'auto' else 'FP8  KV'
    llm = LLM(
        model='meta-llama/Meta-Llama-3-8B-Instruct',
        kv_cache_dtype=kv_dtype,
        gpu_memory_utilization=0.85,
        max_model_len=8192,
        dtype='bfloat16',
    )
    # Warmup
    _ = llm.generate(prompts[:1], SamplingParams(max_tokens=8))
    # Timed run
    t0 = time.perf_counter()
    outputs = llm.generate(prompts, sampling)
    elapsed = time.perf_counter() - t0
    total_tokens = sum(len(o.outputs[0].token_ids) for o in outputs)
    tps = total_tokens / elapsed
    mem_gb = torch.cuda.max_memory_allocated() / 1e9
    results[label] = {'tps': tps, 'mem_gb': mem_gb}
    print('%s: %.1f tok/s  peak GPU mem: %.2f GB' % (label, tps, mem_gb))
    del llm
    torch.cuda.empty_cache()

bf16_tps = results.get('BF16 KV', {}).get('tps', 1)
fp8_tps  = results.get('FP8  KV', {}).get('tps', 1)
print('\nFP8 KV throughput vs BF16 KV: %+.1f%%' % ((fp8_tps / bf16_tps - 1) * 100))

Validate on Long-context Tasks Before Deploying: KV cache quantization error accumulates across long sequences — always validate on tasks requiring coherent long-context reasoning (e.g., passkey retrieval at 32K, multi-document QA, needle-in-a-haystack) before deploying. A model that appears correct on short generations may degrade significantly at 16K+ tokens because quantization error in early token representations compounds through the attention softmax over many decoding steps.

Key Takeaways

  • KV cache memory grows as 2 x layers x heads x seq_len x head_dim x bytes — at long context and large batch it far exceeds model weights.
  • INT8 per-token symmetric quantization halves KV memory with typically <0.05% relative attention output error on standard activations.
  • FP8 E4M3 KV cache matches INT8 quality and is preferable on H100/MI300X where native FP8 tensor cores eliminate dequantization overhead.
  • Per-head scaling outperforms per-tensor scaling for models where specific heads exhibit outlier activation magnitudes — always use per-head or per-token scales for 7B+ models.
  • Pre-RoPE key quantization (KVQuant) substantially reduces key dynamic range, enabling 3-bit average KV precision with near-FP16 perplexity.
  • Attention sink tokens (positions 0–7) attract disproportionate attention scores; keep them in FP16 within a quantized KV cache to prevent quality degradation.
  • vLLM kv_cache_dtype='fp8' is the recommended production setting for H100 serving: zero code change, 1.4–2x memory saving, 5–15% throughput gain from larger batch sizes.
  • Always run long-context validation (passkey retrieval, multi-hop reasoning at >=16K tokens) before deploying KV-quantized models in production.
