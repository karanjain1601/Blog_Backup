Vector Databases for RAG

Vector databases are purpose-built storage and query engines for high-dimensional embedding vectors. In a RAG pipeline the retriever converts queries and documents into dense vectors (typically 768–1536 dimensions from text embedding models) and finds the most similar vectors by approximate nearest neighbour (ANN) search. Doing this at scale — millions of vectors, sub-100ms latency, with metadata filters — requires specialised indexing structures that no traditional database provides. This note covers the two dominant index families (HNSW and IVF-PQ), the problem of filtered ANN search, and a practical comparison of the leading vector databases: FAISS, Qdrant, Weaviate, Pinecone, Chroma, pgvector, and Milvus.

Overview

The core operation in a vector database is k-nearest-neighbour (k-NN) search: given a query vector q, find the k stored vectors with smallest cosine or L2 distance. Exact k-NN over 10M 1536-dim vectors requires computing 10M dot products per query — roughly 300ms on a single CPU core, far too slow for interactive RAG. Approximate nearest neighbour (ANN) algorithms trade a small recall penalty (missing 5–10% of true nearest neighbours) for 10–100x speedup. HNSW (Hierarchical Navigable Small World) is the dominant ANN index for in-memory use; IVF with Product Quantization (IVF-PQ) is the standard for memory-constrained and GPU-accelerated use. Vector databases add operational layers: persistence, live updates, distributed sharding, metadata filtering, and replication — capabilities that FAISS alone does not provide.

ANN vs Exact Search

Exact k-NN (brute force) computes the query vector's distance to every stored vector and returns the true top-k. It is always available as a baseline and requires no index — just a matrix multiply (or cosine similarity) over the embedding matrix. FAISS exposes this as IndexFlatL2 or IndexFlatIP. For small corpora (< 100K vectors) on GPU, exact search is actually faster than ANN because the index traversal overhead of HNSW dominates at small scales. For corpora between 100K and 1M vectors on CPU, HNSW HNSW with ef_search=64 typically achieves 95%+ recall at 10–50x the QPS of brute force. Beyond 10M vectors, IVF-PQ with GPU acceleration is the only option that fits within memory and latency budgets. The right trade-off depends on corpus size, hardware, and acceptable recall.

import faiss
import numpy as np
import time

def benchmark_hnsw_vs_brute(n_vecs: int = 200_000, dim: int = 768,
                             n_queries: int = 100, k: int = 10) -> None:
    """Compare FAISS HNSWFlat (ANN) vs IndexFlatIP (exact) on recall and QPS."""
    rng     = np.random.default_rng(42)
    corpus  = rng.standard_normal((n_vecs, dim)).astype("float32")
    queries = rng.standard_normal((n_queries, dim)).astype("float32")
    faiss.normalize_L2(corpus)
    faiss.normalize_L2(queries)

    # Brute-force exact search
    idx_flat = faiss.IndexFlatIP(dim)
    idx_flat.add(corpus)
    t0 = time.perf_counter()
    D_exact, I_exact = idx_flat.search(queries, k)
    qps_exact = n_queries / (time.perf_counter() - t0)

    # HNSW approximate search (M=32 connections, ef_construction=200)
    idx_hnsw = faiss.IndexHNSWFlat(dim, 32)   # M=32
    idx_hnsw.hnsw.efConstruction = 200
    idx_hnsw.add(corpus)
    idx_hnsw.hnsw.efSearch = 64
    t0 = time.perf_counter()
    D_hnsw, I_hnsw = idx_hnsw.search(queries, k)
    qps_hnsw = n_queries / (time.perf_counter() - t0)

    # Compute recall@k: fraction of exact top-k found by HNSW
    recall = np.mean([len(set(I_hnsw[i]) & set(I_exact[i])) / k for i in range(n_queries)])
    print(f"Brute force QPS : {qps_exact:>8.1f}")
    print(f"HNSW QPS        : {qps_hnsw:>8.1f}  ({qps_hnsw/qps_exact:.1f}x speedup)")
    print(f"HNSW recall@{k}  : {recall:.4f}")

HNSW Index

HNSW (Malkov & Yashunin, 2018) builds a multi-layer proximity graph over the vector space. Each vector is inserted into a random subset of layers; the top layer is sparse (long-range connections) and the bottom layer is dense (fine-grained connections). Search starts at the top layer, greedily navigating towards the query, then descends through layers to increasingly fine-grained neighbourhoods. The key parameters are M (number of connections per node per layer, typically 16–64), ef_construction (beam width during index build, higher = better recall, slower build), and ef_search (beam width during search, higher = better recall, slower query). HNSW is the preferred index for RAM-resident collections up to ~10M vectors. Its main limitation is memory: each vector stores M*4 bytes of graph edges plus the full-precision embedding, roughly 2–4x the raw embedding size.

HNSW recall scales predictably with ef_search. At ef_search=16, recall@10 is typically 92–94%. At ef_search=64, recall@10 is 97–99%. At ef_search=200, recall@10 approaches 99.9% with a 3–4x query latency cost. For most RAG applications, ef_search=64 with recall@10 ≥ 0.97 is the right operating point. The index build time scales as O(n * M * log(n)) and is typically 10–30 minutes for 1M 768-dim vectors on 16 CPU cores. HNSW indexes are read-optimised: adding new vectors is O(M * log(n)) but rebuilding is required to delete vectors, making it less suited for corpora with frequent deletions.

IVF with PQ Compression

IVF (Inverted File Index) partitions the vector space into nlist Voronoi cells using k-means clustering. At query time, only nprobe cells are searched, reducing computation by approximately nlist/nprobe. IVF alone does not compress the vectors: each stored vector still occupies dim4 bytes of float32. Product Quantization (PQ) compresses each vector from dim4 bytes to m bytes by splitting the vector into m subvectors and quantizing each subvector to 8 bits (256 centroids). A 1536-dim float32 vector occupies 6144 bytes; with PQ m=96, it compresses to 96 bytes (64x compression). The combined IVF-PQ index fits 100M vectors in ~10GB RAM, versus ~600GB for flat float32 — enabling billion-scale search on a single node. The recall penalty for PQ compression is typically 3–8% versus full float32, partially recoverable by re-ranking top-PQ results against their original vectors.

import psycopg2
import numpy as np
import time
from pgvector.psycopg2 import register_vector

CONN_STR = "postgresql://user:password@localhost:5432/vectordb"

def setup_pgvector_table(conn, dim: int = 1536) -> None:
    """Create a table with a pgvector column and both IVFFlat and exact indexes."""
    with conn.cursor() as cur:
        cur.execute("CREATE EXTENSION IF NOT EXISTS vector;")
        cur.execute(f"""
            CREATE TABLE IF NOT EXISTS embeddings (
                id      BIGSERIAL PRIMARY KEY,
                source  TEXT,
                content TEXT,
                embedding VECTOR({dim})
            );
        """)
        conn.commit()

def insert_embeddings(conn, records: list) -> None:
    """Bulk insert (id, source, content, embedding) tuples."""
    with conn.cursor() as cur:
        for rec in records:
            cur.execute(
                "INSERT INTO embeddings (source, content, embedding) VALUES (%s, %s, %s)",
                (rec["source"], rec["content"], rec["embedding"].tolist())
            )
    conn.commit()

def build_ivfflat_index(conn, lists: int = 100) -> None:
    """Build IVFFlat index for approximate cosine search."""
    with conn.cursor() as cur:
        cur.execute(f"""
            CREATE INDEX IF NOT EXISTS emb_ivfflat
            ON embeddings USING ivfflat (embedding vector_cosine_ops)
            WITH (lists = {lists});
        """)
    conn.commit()
    print(f"IVFFlat index built with {lists} lists")

def query_top_k(conn, query_vec: np.ndarray, k: int = 10) -> list:
    """Cosine ANN search: ORDER BY embedding <=> query LIMIT k."""
    with conn.cursor() as cur:
        cur.execute(
            "SELECT id, source, content, 1 - (embedding <=> %s) AS score "
            "FROM embeddings ORDER BY embedding <=> %s LIMIT %s",
            (query_vec.tolist(), query_vec.tolist(), k)
        )
        return cur.fetchall()

# Example usage
if __name__ == "__main__":
    conn = psycopg2.connect(CONN_STR)
    register_vector(conn)
    setup_pgvector_table(conn, dim=1536)
    build_ivfflat_index(conn, lists=100)
    q = np.random.randn(1536).astype(np.float32)
    q /= np.linalg.norm(q)
    results = query_top_k(conn, q, k=10)
    print(f"Top-10 results: {len(results)} rows returned")

Metadata Filtering

Production RAG systems almost always need filtered search: find the 10 most similar embeddings to query q among documents where metadata.source == 'arxiv' and metadata.year >= 2023. Naively, the filter can be applied post-search (retrieve top-K ANN results then filter to those matching the predicate) or pre-filter (filter the corpus to matching documents then search within them). Post-filter is fast but misses results if the matching subset is a small fraction of the corpus. Pre-filter produces correct recall but is slow if the filter matches many documents (must search a large unindexed subset). Purpose-built vector databases (Qdrant, Weaviate, Pinecone) implement filtered HNSW: they maintain per-filter segment indexes or use payload-aware graph traversal to satisfy filters within ANN search without sacrificing recall. pgvector applies the WHERE clause before the ORDER BY vector_ops, which falls back to sequential scan on small filtered sets — fast for many filters, slow for unselective ones.

import numpy as np
import time
from qdrant_client import QdrantClient
from qdrant_client.models import (
    Distance, VectorParams, PointStruct,
    Filter, FieldCondition, MatchValue, Range
)

def setup_qdrant_collection(client: QdrantClient, name: str, dim: int = 1536) -> None:
    """Create a Qdrant collection with cosine distance HNSW index."""
    client.recreate_collection(
        collection_name=name,
        vectors_config=VectorParams(size=dim, distance=Distance.COSINE),
    )
    print(f"Collection '{name}' created (dim={dim}, distance=COSINE)")

def upsert_points(client: QdrantClient, name: str,
                  embeddings: np.ndarray, metadata: list) -> None:
    """Batch upsert embeddings with metadata payloads."""
    points = [
        PointStruct(id=i, vector=emb.tolist(), payload=meta)
        for i, (emb, meta) in enumerate(zip(embeddings, metadata))
    ]
    client.upsert(collection_name=name, points=points)
    print(f"Upserted {len(points)} points")

def filtered_search(client: QdrantClient, name: str,
                    query: np.ndarray, source: str, k: int = 10) -> list:
    """ANN search filtered to documents from a specific source."""
    flt = Filter(must=[FieldCondition(key="source", match=MatchValue(value=source))])
    t0  = time.perf_counter()
    hits = client.search(collection_name=name, query_vector=query.tolist(),
                         query_filter=flt, limit=k)
    latency_ms = (time.perf_counter() - t0) * 1000
    print(f"Filtered search (source='{source}'): {len(hits)} results in {latency_ms:.1f}ms")
    return hits

# Demo: insert 10K arxiv + 10K wikipedia embeddings, search only arxiv
if __name__ == "__main__":
    client = QdrantClient(":memory:")
    setup_qdrant_collection(client, "papers", dim=128)   # small dim for demo
    n = 10_000
    rng  = np.random.default_rng(0)
    embs = rng.standard_normal((2 * n, 128)).astype(np.float32)
    meta = [{"source": "arxiv"}] * n + [{"source": "wikipedia"}] * n
    upsert_points(client, "papers", embs, meta)
    q = rng.standard_normal(128).astype(np.float32)
    results = filtered_search(client, "papers", q, source="arxiv", k=10)

Vector Database Comparison

FAISS is the fastest ANN library for in-memory search but is not a database — it has no persistence, replication, live updates, or query language. It is ideal as a building block inside an application server. Qdrant is the leading open-source vector database for production RAG: it has excellent filtered HNSW, GRPC and REST APIs, payload indexing, and a Rust core that delivers high QPS. Weaviate adds native BM25 keyword search and hybrid (vector + BM25) ranking out-of-the-box, making it strong for RAG systems that need lexical fallback. Pinecone is the easiest to get started with (no infrastructure to manage) but is fully proprietary and expensive at scale. Chroma is the best choice for local development and prototyping — simple Python API, no server required. pgvector is compelling for teams already on Postgres who want to avoid a separate database dependency, though its QPS falls behind dedicated vector databases at >1M vectors. Milvus handles billion-scale deployments and GPU-accelerated search, making it the right choice for very large corpora.

When to Use a Dedicated Vector Database: For fewer than 10M vectors on a single machine, FAISS HNSW with a metadata store (SQLite or Postgres) beats dedicated vector databases in raw performance and operational simplicity — only move to a dedicated vector database when you need distributed scale, live updates without full index rebuilds, built-in replication, or managed filtered search across payload fields. Start with Chroma locally, validate your embedding strategy, then migrate to Qdrant or pgvector for production.

Operational Considerations

Running a vector database in production requires planning for index persistence (HNSW indexes must be saved to disk and loaded on restart — Qdrant snapshots, FAISS write_index), index updates (HNSW insert is fast but deletion requires segment merges in Qdrant or a full rebuild in FAISS), memory capacity (a 1536-dim float32 HNSW index for 10M vectors consumes ~60GB RAM with M=32), and monitoring (track p99 query latency, recall sampled against brute-force ground truth, and index size growth). For multi-tenant RAG (many users with separate document collections), use namespaces (Pinecone) or collections (Qdrant/Chroma) rather than payload filters, as per-tenant isolation prevents data leakage and simplifies deletion. Always test filtered search recall specifically — filters that match <5% of the corpus can degrade filtered ANN recall to <70%, far below the 97% unfiltered recall benchmark.

  • Persist HNSW indexes to disk (Qdrant snapshot, faiss.write_index) — in-memory indexes are lost on restart
  • Monitor p99 query latency and sampled recall@10 against brute-force ground truth weekly
  • For M=32 HNSW and 1536-dim float32, budget ~6KB per vector (3.2KB embedding + ~2.8KB graph edges)
  • Test filtered search recall on your specific filter selectivity — narrow filters degrade ANN recall significantly
  • Use separate collections or namespaces for multi-tenant isolation, not payload filters
  • Prefer cosine similarity (normalised L2) for text embeddings from OpenAI/Cohere/sentence-transformers
import numpy as np
import time
import faiss
from qdrant_client import QdrantClient
from qdrant_client.models import Distance, VectorParams, PointStruct
import chromadb

N_VECS   = 100_000
DIM      = 1536
N_QUERY  = 1_000
K        = 10
rng      = np.random.default_rng(99)
corpus   = rng.standard_normal((N_VECS, DIM)).astype("float32")
queries  = rng.standard_normal((N_QUERY, DIM)).astype("float32")
faiss.normalize_L2(corpus)
faiss.normalize_L2(queries)

def bench_faiss_hnsw() -> dict:
    idx = faiss.IndexHNSWFlat(DIM, 32)
    idx.hnsw.efConstruction = 200
    t0 = time.perf_counter(); idx.add(corpus); build_s = time.perf_counter() - t0
    idx.hnsw.efSearch = 64
    t0 = time.perf_counter(); idx.search(queries, K); qps = N_QUERY / (time.perf_counter() - t0)
    return {"db": "FAISS HNSW", "build_s": round(build_s, 1), "qps": round(qps), "mem_mb": round(idx.ntotal * DIM * 4 / 1e6, 0)}

def bench_qdrant() -> dict:
    client = QdrantClient(":memory:")
    client.recreate_collection("bench", vectors_config=VectorParams(size=DIM, distance=Distance.COSINE))
    pts = [PointStruct(id=i, vector=corpus[i].tolist(), payload={}) for i in range(N_VECS)]
    t0 = time.perf_counter(); client.upsert("bench", points=pts); build_s = time.perf_counter() - t0
    t0 = time.perf_counter()
    for q in queries: client.search("bench", query_vector=q.tolist(), limit=K)
    qps = N_QUERY / (time.perf_counter() - t0)
    return {"db": "Qdrant", "build_s": round(build_s, 1), "qps": round(qps), "mem_mb": "N/A"}

results = [bench_faiss_hnsw(), bench_qdrant()]
print(f"{'Database':<15} {'Build(s)':>10} {'QPS':>8} {'Mem(MB)':>10}")

Key Takeaways

Vector databases power the retrieval stage of RAG by providing fast approximate nearest neighbour search over high-dimensional embeddings. HNSW is the dominant in-memory ANN index, delivering 97–99% recall@10 at 10–100x the QPS of brute force for corpora up to 10M vectors. IVF-PQ enables billion-scale search by compressing embeddings 64x with a 3–8% recall penalty. Metadata filtering is a critical production requirement — choose a database with native filtered HNSW (Qdrant, Weaviate, Pinecone) to maintain ANN recall over narrow filters. For small-to-medium scale (< 10M vectors), FAISS HNSW plus a Postgres metadata store is the highest-performance option. For teams wanting a managed solution with strong filtering, Qdrant Cloud or Pinecone are the production-ready choices.

  • HNSW with M=32, ef_construction=200, ef_search=64 delivers 97–99% recall@10 at near-optimal QPS
  • IVF-PQ compresses float32 vectors 64x (1536-dim to 96 bytes) for billion-scale in-memory search
  • Always benchmark filtered search recall on your specific filter selectivity — narrow filters can hurt recall severely
  • Qdrant is the best open-source option for production RAG: native filtered HNSW, Rust core, managed cloud available
  • pgvector is the right choice if you are already on Postgres and need fewer than 1M vectors
  • Start with Chroma locally, validate embeddings, then migrate to a dedicated vector database for production
