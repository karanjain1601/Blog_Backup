Document Chunking Strategies for RAG

Chunking is the process of splitting source documents into smaller retrieval units before embedding and indexing them in a vector store. The choice of chunking strategy is one of the highest-leverage decisions in a RAG pipeline: chunks that are too small lose the context needed to answer multi-sentence questions; chunks that are too large dilute the semantic signal with irrelevant content and consume unnecessary LLM context tokens. Modern RAG systems choose from fixed-size, recursive character, semantic, sentence-window, and hierarchical (parent-child) chunking, each making different tradeoffs between coherence, retrieval precision, implementation complexity, and preprocessing cost.

Overview

Every RAG pipeline begins with a corpus of source documents — PDFs, web pages, code files, or database exports. Before these documents can be embedded and searched, they must be split into retrieval units small enough to be semantically focused but large enough to carry useful context. The chunking decision affects three key pipeline properties: (1) retrieval precision — whether the chunk containing the answer is ranked at position 1 rather than position 10; (2) context coherence — whether the retrieved chunk contains enough surrounding text for the LLM to generate a complete, accurate answer; and (3) index size and cost — chunk count directly determines how many embeddings must be stored, computed, and compared at query time. No single strategy dominates on all three; the right choice depends on document structure, query type, and latency budget.

Fixed-Size Chunking

Fixed-size chunking splits a document every N characters or tokens, regardless of content structure. It is the simplest strategy to implement and the fastest to preprocess, requiring no embedding step and no linguistic analysis during chunking. The two key parameters are chunk_size (the target size in characters or tokens) and chunk_overlap (the number of characters shared between consecutive chunks). Overlapping chunks prevent answers from being cut at chunk boundaries: a concept that spans the junction between two non-overlapping chunks may be retrievable from neither; with overlap of 10–20% of chunk_size, at least one chunk will contain the full span. Fixed-size chunking works adequately for uniform-format documents such as news articles or structured database records, but degrades on rich-format documents like PDFs or HTML where semantic boundaries rarely align with character counts.

from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain.schema import Document
import json

with open("document.txt", "r", encoding="utf-8") as f:
    raw_text = f.read()

# RecursiveCharacterTextSplitter tries separators in order:
# paragraph breaks -> line breaks -> sentence ends -> spaces -> chars
splitter = RecursiveCharacterTextSplitter(
    chunk_size=512,
    chunk_overlap=50,
    length_function=len,
    add_start_index=True,
)

chunks = splitter.split_text(raw_text)
docs   = splitter.create_documents([raw_text])

print(f"Document : {len(raw_text):,} chars")
print(f"Chunks   : {len(chunks)}  avg={sum(len(c) for c in chunks)/len(chunks):.0f} chars")

for i, chunk in enumerate(chunks[:3]):
    print(f"\n--- Chunk {i} ({len(chunk)} chars, start={docs[i].metadata.get('start_index')}) ---")
    print(chunk[:120] + "..." if len(chunk) > 120 else chunk)

# Verify overlap: tail of chunk 0 should appear in head of chunk 1
if len(chunks) >= 2:
    overlap_sample = chunks[0][-30:]
    print(f"\nOverlap verified: {overlap_sample.strip()[:20]!r} in chunk 1: {overlap_sample in chunks[1]}")

The RecursiveCharacterTextSplitter from LangChain is the recommended default for most RAG applications. Unlike a plain CharacterTextSplitter, it tries a list of separators in decreasing order of preference — double-newlines (paragraph breaks), single newlines, periods, spaces, then individual characters — so the splitter honours natural semantic units as much as possible within the chunk size budget. The add_start_index=True flag stores the character offset of each chunk in its metadata, making it easy to highlight the source span in a UI. Setting chunk_overlap=50 (about 10% of chunk_size=512) is a good starting point; increase to 100 for documents with dense factual sentences.

Recursive Character Splitting

Recursive character splitting generalises fixed-size chunking by respecting a hierarchy of natural separators. The algorithm works as follows: attempt to split the text using the highest-priority separator (typically double-newline, representing paragraph breaks). If any resulting piece is still larger than chunk_size, recursively apply the next separator (single newline, then sentence-end period, then space). This ensures that the smallest possible linguistic unit is sacrificed first. For well-structured documents like technical documentation or markdown, the overwhelming majority of chunks will end at paragraph or sentence boundaries rather than mid-word. The key advantage over simple fixed-size chunking is that the resulting chunks are grammatically coherent and interpretable in isolation, which improves both embedding quality and LLM answer generation.

import numpy as np
from sentence_transformers import SentenceTransformer
from sklearn.metrics.pairwise import cosine_similarity

embed_model = SentenceTransformer("all-MiniLM-L6-v2")

def semantic_chunk(text: str, threshold: float = 0.4) -> list:
    """Split text at semantic breakpoints: low cosine similarity between consecutive sentences."""
    sentences = [s.strip() for s in text.split(". ") if len(s.strip()) > 5]
    if len(sentences) < 2:
        return sentences
    embeddings = embed_model.encode(sentences, batch_size=32, show_progress_bar=False)
    sims = [cosine_similarity([embeddings[i]], [embeddings[i + 1]])[0][0]
            for i in range(len(embeddings) - 1)]
    chunks, current = [], [sentences[0]]
    for i, sim in enumerate(sims):
        if sim < threshold:
            chunks.append(". ".join(current) + ".")
            current = [sentences[i + 1]]
        else:
            current.append(sentences[i + 1])
    if current:
        chunks.append(". ".join(current))
    print(f"Sentences: {len(sentences)} | Avg sim: {np.mean(sims):.3f} | Splits: {sum(s < threshold for s in sims)} | Chunks: {len(chunks)}")
    return chunks

text = ("Attention mechanisms compute weighted sums over values. "
        "Query and key vectors determine attention weights. "
        "The cat sat on the warm sunny mat. "
        "Fluffy animals enjoy comfortable resting spots. ")
for i, c in enumerate(semantic_chunk(text)):
    print(f"Chunk {i}: {c[:90]}")

Semantic Chunking

Semantic chunking detects topic shifts by embedding each sentence and measuring cosine similarity between consecutive sentence embeddings. When similarity drops below a threshold (typically 0.3–0.5), a chunk boundary is inserted. This produces semantically cohesive chunks — each chunk discusses a single coherent topic. The cost is preprocessing time: semantic chunking requires an embedding model call for every sentence in the corpus, making it 10–100x slower than fixed-size chunking during indexing. It is most valuable for heterogeneous documents where topic shifts occur within paragraphs, such as encyclopaedia articles, research paper related-work sections, or FAQ documents where questions and answers on different topics are interleaved.

Sentence Window Retrieval

Sentence window retrieval is a two-stage approach: index each sentence individually as the retrieval unit (maximising retrieval precision by making each sentence an atomic target), but when a sentence is retrieved, expand the context window to include the surrounding ±2–3 sentences before passing to the LLM. This technique combines the best properties of small-chunk precision (only the most relevant anchor sentence is retrieved) with the context richness of larger chunks (the surrounding sentences supply enough background for a coherent answer). The technique was popularised by LlamaIndex's SentenceWindowNodeParser and works particularly well for factoid and definition questions where the exact relevant sentence is known but a single sentence alone is insufficient context.

import numpy as np
from sentence_transformers import SentenceTransformer
import faiss

embed_model = SentenceTransformer("all-MiniLM-L6-v2")

def build_sentence_index(text: str):
    """Index each sentence; store positions for window expansion at retrieval time."""
    sents = [s.strip() for s in text.split(". ") if s.strip()]
    embs  = embed_model.encode(sents, normalize_embeddings=True).astype(np.float32)
    index = faiss.IndexFlatIP(embs.shape[1])
    index.add(embs)
    return sents, index

def window_retrieve(query: str, sents, index, window: int = 2, top_k: int = 3):
    """Retrieve top_k anchor sentences; expand each to ±window neighbours for LLM context."""
    q    = embed_model.encode([query], normalize_embeddings=True).astype(np.float32)
    scores, hits = index.search(q, top_k)
    for score, i in zip(scores[0], hits[0]):
        lo, hi  = max(0, int(i) - window), min(len(sents) - 1, int(i) + window)
        context = ". ".join(sents[lo: hi + 1])
        print(f"Score {score:.3f} | anchor: {sents[i][:60]}")
        print(f"  Context ({hi - lo + 1} sents): {context[:130]}")

doc = ("Transformers use self-attention to model dependencies. "
       "Self-attention computes pairwise token interactions. "
       "Feed-forward layers transform each position non-linearly. "
       "Layer normalisation stabilises training activations. "
       "Residual connections enable gradient flow in deep networks.")
sents, idx = build_sentence_index(doc)
window_retrieve("how does attention work in transformers", sents, idx)

The sentence window technique requires storing the full document text alongside the sentence index so that the window can be reconstructed at query time. In practice, each indexed sentence node stores its position (sentence index) and a reference to the parent document. When a sentence is retrieved, the surrounding ±2 sentences are fetched from the document store and concatenated to form the LLM context. This adds one lightweight key-value lookup per retrieved chunk but no additional vector search. The window size (typically 2–3) is a tunable hyperparameter: larger windows provide more context but increase LLM token consumption and may introduce noise.

Hierarchical (Parent-Child) Chunking

Hierarchical chunking creates two levels of chunk granularity: small child chunks (128–256 tokens) for high-precision retrieval, and large parent chunks (512–1024 tokens) for rich LLM context. The vector index stores embeddings of the child chunks only. At query time, the top-k child chunks are retrieved by semantic similarity, and then each child chunk is replaced with its parent chunk before passing to the LLM. This means the LLM sees a larger, more coherent context window while retrieval still benefits from the precision of small embeddings. LlamaIndex implements this as ParentDocumentRetriever (also available in LangChain) with configurable child_chunk_size and parent_chunk_size parameters. The approach is especially effective for long-form documents where individual facts are embedded in a rich surrounding context.

import numpy as np
from langchain.text_splitter import RecursiveCharacterTextSplitter
from sentence_transformers import SentenceTransformer
import faiss

def build_hybrid_index(text: str, child_size: int = 256, parent_size: int = 1024):
    """Parent-child chunking: embed small child chunks, retrieve parent for LLM context."""
    parent_splitter = RecursiveCharacterTextSplitter(chunk_size=parent_size, chunk_overlap=0)
    child_splitter  = RecursiveCharacterTextSplitter(chunk_size=child_size,  chunk_overlap=20)
    parents  = parent_splitter.split_text(text)
    children, child_to_parent = [], []
    for p_idx, parent in enumerate(parents):
        kids = child_splitter.split_text(parent)
        children.extend(kids)
        child_to_parent.extend([p_idx] * len(kids))
    model = SentenceTransformer("all-MiniLM-L6-v2")
    embs  = model.encode(children, normalize_embeddings=True).astype(np.float32)
    index = faiss.IndexFlatIP(embs.shape[1])
    index.add(embs)
    print(f"Parents: {len(parents)}  Children: {len(children)}  Avg children/parent: {len(children)/max(len(parents),1):.1f}")
    return parents, children, child_to_parent, index, model

def hierarchical_retrieve(query: str, parents, children, c2p, index, model, top_k: int = 3):
    q      = model.encode([query], normalize_embeddings=True).astype(np.float32)
    _, hits = index.search(q, top_k)
    seen_parents = set()
    for child_idx in hits[0]:
        p_idx = c2p[child_idx]
        if p_idx not in seen_parents:
            seen_parents.add(p_idx)
            print(f"Child match: {children[child_idx][:60]}")
            print(f"  -> Parent context ({len(parents[p_idx])} chars): {parents[p_idx][:120]}...")

Chunk Size Tradeoffs

Optimal chunk size is corpus-dependent but follows a consistent pattern across benchmarks. Chunks of 128–256 tokens give high retrieval precision — the top-ranked chunk almost always contains the answer sentence — but often lack enough surrounding context for the LLM to generate a complete response. Chunks of 512 tokens balance precision and context for most question-answer datasets and represent the most common default in production RAG systems. Chunks of 1024+ tokens improve answer quality on multi-sentence reasoning questions but reduce retrieval precision because each chunk contains many topics, diluting the embedding signal. The empirical optimum for most English-language document corpora is 400–600 tokens with 10–15% overlap. Domain-specific corpora (legal, medical, technical) often benefit from larger chunks (768–1024 tokens) because answers require more surrounding context to be interpretable.

import numpy as np
from langchain.text_splitter import RecursiveCharacterTextSplitter
from sentence_transformers import SentenceTransformer
import faiss

def chunk_size_sweep(text: str, questions: list, answers: list,
                     chunk_sizes: list = None, top_k: int = 5) -> dict:
    """Index the same corpus at multiple chunk sizes; measure Recall@k for each."""
    if chunk_sizes is None:
        chunk_sizes = [128, 256, 512, 1024]
    model   = SentenceTransformer("all-MiniLM-L6-v2")
    results = {}
    for cs in chunk_sizes:
        splitter = RecursiveCharacterTextSplitter(chunk_size=cs, chunk_overlap=cs // 10)
        chunks   = splitter.split_text(text)
        embs     = model.encode(chunks, normalize_embeddings=True).astype(np.float32)
        index    = faiss.IndexFlatIP(embs.shape[1])
        index.add(embs)
        hits = 0
        for q, a in zip(questions, answers):
            q_emb = model.encode([q], normalize_embeddings=True).astype(np.float32)
            _, idxs = index.search(q_emb, top_k)
            retrieved = " ".join(chunks[i] for i in idxs[0] if i < len(chunks))
            if a.lower() in retrieved.lower():
                hits += 1
        results[cs] = {"recall_at_k": hits / max(len(questions), 1), "n_chunks": len(chunks)}
    print(f"{'Chunk':>8}  {'N chunks':>10}  {'Recall@5':>10}")
    for cs, r in results.items():
        print(f"{cs:>8}  {r['n_chunks']:>10}  {r['recall_at_k']:>10.3f}")
    return results

Overlap is Free Insurance: Overlapping chunks (overlap=10–20% of chunk size) prevent answers from falling at chunk boundaries — a question about a concept split across two chunks may retrieve neither correctly without overlap. At chunk_size=512, setting chunk_overlap=50 costs only 10% more storage and index size but consistently improves Recall@5 by 5–10 percentage points on boundary-sensitive queries. Always enable overlap unless index size is a hard constraint.

Key Takeaways

Chunking is not a set-and-forget decision: the optimal strategy depends on document structure, query distribution, and available compute. Start with RecursiveCharacterTextSplitter at chunk_size=512 and chunk_overlap=50 as a strong baseline for most text corpora. If retrieval precision is insufficient (answers present in corpus but not in top-5), move to sentence-window or semantic chunking. If answer generation quality is insufficient (relevant chunks retrieved but LLM cannot form a complete answer), move to parent-child chunking or increase chunk size. Always measure Recall@k and answer accuracy on a held-out evaluation set before committing to a strategy. The combination of semantic chunking for preprocessing and sentence-window expansion for retrieval represents the current practical best practice for production RAG systems.

  • Start with RecursiveCharacterTextSplitter at chunk_size=512, chunk_overlap=50 — works for 80% of corpora
  • Always enable overlap (10–20% of chunk_size) to prevent boundary-split answer misses
  • Semantic chunking produces the most coherent chunks but is 10–100x slower to index
  • Sentence-window: index sentences, retrieve parents — best precision-context tradeoff for factoid QA
  • Parent-child: embed small chunks for precision, expand to large chunks for LLM context
  • Run a chunk-size sweep (128/256/512/1024) on your specific corpus before production; optimal size varies
  • Evaluate with Recall@5 on 50–100 representative questions before committing to any strategy
