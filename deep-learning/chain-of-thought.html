  • topic: deep-learning
  • status: published

Chain-of-Thought Prompting

Standard few-shot prompting provides labelled examples that anchor an LLM's output format and task distribution. But on multi-step arithmetic, commonsense reasoning, and symbolic manipulation tasks, even 8-shot prompting plateaus well below human performance — the model is asked to compress multi-step reasoning into a single token prediction. Chain-of-thought (CoT) prompting, introduced by Wei et al. (2022, "Chain-of-Thought Prompting Elicits Reasoning in Large Language Models"), extends few-shot prompting by augmenting each demonstration with a step-by-step reasoning trace that leads to the answer. When the model sees these annotated examples, it learns to generate its own reasoning chain before producing the final answer. This simple modification dramatically improves accuracy on reasoning tasks: from 18% to 57% on GSM8K (grade school math) for PaLM 540B, and from 35% to 83% on the AQuA-RAT math word problem benchmark. Chain-of-thought prompting does not require any weight updates — it is purely a prompting strategy — but its benefits are strongly model-scale dependent.

Overview

Chain-of-thought prompting augments the k demonstrations in a few-shot prompt with natural-language reasoning steps that explain how to derive the answer from the input. Each demonstration takes the form: question → reasoning chain → final answer. The model, having seen these annotated examples, learns to produce a reasoning chain for each new input before generating its final answer. The reasoning chain serves two purposes: it decomposes the problem into manageable sub-steps, and it allocates additional computational capacity (more tokens of generation) to the reasoning process. Wei et al. tested CoT prompting on GPT-3 (175B), LaMDA (137B), PaLM (540B), and UL2 (20B) and found that CoT only helps models with approximately 100 billion or more parameters — smaller models produce plausible-sounding but systematically incorrect reasoning chains, which can actually hurt accuracy relative to direct answering. This scale sensitivity is a critical constraint on when to apply CoT.

Few-Shot CoT Prompting

Few-shot CoT provides k example triplets of the form (question, reasoning steps, answer). The reasoning steps are written in natural language and explicitly decompose the problem: identifying relevant quantities, converting units, applying relationships, performing arithmetic, and verifying the result against the question. The format is critical: the reasoning must appear before the final answer, clearly delineated (typically by "The answer is:" or "Therefore:"). The final answer extraction must be consistent across all demonstrations — if some use "= N" and others use "The answer is N", the model's answer extraction becomes unreliable. On GSM8K, 8-shot CoT with 3–4 sentence reasoning chains per example raises PaLM 540B from 17.9% (direct) to 56.9% (CoT). This 39-point improvement is achieved purely through prompt engineering with no fine-tuning.

import openai
import re

client = openai.OpenAI()

COT_EXAMPLES = [
    {"q": "Janet has 3 apples. She buys 5 more and gives 2 to her friend. How many does she have?",
     "r": "Janet starts with 3 apples. She buys 5 more: 3 + 5 = 8. She gives 2 away: 8 - 2 = 6.",
     "a": "6"},
    {"q": "A store sells pens for $1.50 each. Maria buys 4 pens and pays with a $10 bill. How much change?",
     "r": "4 pens cost 4 x $1.50 = $6.00. Change from $10: $10.00 - $6.00 = $4.00.",
     "a": "$4.00"},
]

def build_cot_prompt(question, examples, use_cot=True):
    msgs = [{"role": "system", "content": "Solve the math problem. Show your work then state the answer."}]
    for ex in examples:
        q_text = ex["q"]
        if use_cot:
            a_text = ex["r"] + f" The answer is {ex['a']}."
        else:
            a_text = f"The answer is {ex['a']}."
        msgs += [{"role": "user", "content": q_text}, {"role": "assistant", "content": a_text}]
    msgs.append({"role": "user", "content": question})
    return msgs

def solve(question, examples, use_cot):
    msgs = build_cot_prompt(question, examples, use_cot)
    resp = client.chat.completions.create(model="gpt-4o-mini", messages=msgs, max_tokens=200)
    return resp.choices[0].message.content.strip()

Q = "Tom has 24 cookies. He eats a third of them and shares half the rest with a friend. How many does he keep?"
print("Direct:", solve(Q, COT_EXAMPLES, use_cot=False))
print("CoT:   ", solve(Q, COT_EXAMPLES, use_cot=True))

The direct-answer prompt collapses the multi-step reasoning into a single prediction, which forces the model to perform arithmetic in one shot — a task it frequently gets wrong even when it can articulate the correct procedure given space. The CoT prompt allocates generation capacity to the reasoning steps, making each sub-computation explicit. The model's attention mechanism can attend to intermediate results it has already generated (e.g., "24/3 = 8 cookies eaten") when computing subsequent steps, effectively giving it a scratchpad. This is the core mechanism by which CoT works: it converts an implicit, one-shot reasoning task into a sequential decomposition where each step has its own prediction and can be conditioned on by subsequent steps.

Why CoT Works

Several complementary explanations account for CoT's effectiveness. First, the sequential token generation process provides a scratchpad for intermediate computations — the model can refer back to quantities it has already written when producing subsequent steps. Second, chain-of-thought reasoning allocates proportionally more tokens to complex problems, whereas direct answering gives every problem the same (zero) explicit reasoning budget. Third, CoT demonstrations teach the model problem-decomposition strategies that generalise to new problems: how to identify the relevant quantities, which operations to apply, and in what order. Fourth, the reasoning chain provides a natural location for error localisation: when the final answer is wrong, examining the chain often reveals exactly which step failed, making CoT prompts easier to debug and improve than black-box direct-answer prompts. The consistent finding that CoT helps large models but hurts small models is explained by the fact that small models lack sufficient capability to generate correct reasoning chains — their reasoning is plausible-sounding but wrong, which actively misleads the answer generation.

import openai

client = openai.OpenAI()

WEAK_COT = """Q: A train travels 60 mph for 2.5 hours. How far does it go?
Reasoning: 60 x 2.5 = 150.
Answer: 150 miles."""

STRONG_COT = """Q: A train travels 60 mph for 2.5 hours. How far does it go?
Reasoning: Identify the knowns: speed = 60 mph, time = 2.5 hours.
Apply distance formula: distance = speed x time = 60 x 2.5.
Compute: 60 x 2 = 120, 60 x 0.5 = 30, total = 120 + 30 = 150 miles.
Unit check: mph x hours = miles. Answer is in miles as required.
Answer: 150 miles."""

TARGET_Q = "A cyclist travels at 15 mph for 40 minutes and then at 20 mph for 30 minutes. Total distance?"

def solve_with_style(question, cot_example, label):
    msgs = [{"role": "system", "content": "Solve math problems step by step."},
            {"role": "user", "content": cot_example.split('Q: ')[1].split('\nReasoning')[0]},
            {"role": "assistant", "content": "Reasoning: " + cot_example.split('Reasoning: ')[1]},
            {"role": "user", "content": question}]
    resp = client.chat.completions.create(model="gpt-4o-mini", messages=msgs, max_tokens=200)
    result = resp.choices[0].message.content.strip()
    print(f"--- {label} CoT ---\n{result}\n")
    return result

solve_with_style(TARGET_Q, WEAK_COT, "Weak")
solve_with_style(TARGET_Q, STRONG_COT, "Strong")

The contrast between weak and strong CoT examples is substantial. A weak CoT example shows only the final computation without decomposing the problem structure, teaching the model a shallow pattern-matching approach. A strong CoT example identifies the relevant knowns, states the applicable formula or principle, performs each sub-calculation explicitly with intermediate values, checks units, and arrives at the answer through a verifiable chain. Strong CoT examples transfer better to novel problems because they encode problem-solving strategy, not just problem-specific computation. The cost of writing strong CoT examples is higher, but each example used across many API calls makes the fixed annotation cost negligible.

Task Categories That Benefit

Chain-of-thought prompting does not universally improve performance — the benefit depends heavily on the task type and whether the task requires multi-step reasoning. On single-step tasks (simple fact lookup, direct classification with an unambiguous answer), CoT adds verbosity without improving accuracy and can slightly hurt performance by introducing opportunities for the model to reason itself into a wrong answer. On multi-step tasks (arithmetic word problems, multi-hop reasoning, symbolic manipulation), CoT provides large gains because the decomposition into intermediate steps aligns with the structure of the correct solution. Commonsense reasoning tasks occupy a middle ground — some questions require chain reasoning ("What would happen if..." counterfactuals) while others are effectively single-hop lookups. Code generation is a special case: chain-of-thought prompting naturally maps to pseudocode or algorithm decomposition before implementation, and models consistently produce better code when first asked to outline the approach.

Designing Effective CoT Examples

The quality of CoT demonstrations directly determines the ceiling of CoT prompting performance. High-quality CoT examples share several characteristics: they decompose the problem into the minimal number of clearly labelled sub-steps required to reach the answer; they track relevant units and quantities explicitly through each step; they include a brief check that the answer is plausible given the question constraints; and they use a consistent format for the final answer (a single number, a clearly delineated phrase, or a structured object). The number of reasoning steps should be proportional to the problem complexity — using a 6-step chain for a 2-step problem teaches the model to over-elaborate, while using a 2-step chain for a 6-step problem teaches it to skip critical intermediate calculations. Diversity across demonstrations is also important: if all 4-shot examples involve the same operation (e.g., multiplication), the model may apply that operation regardless of what the test problem actually requires.

  • Decompose each example into the minimal number of steps required — do not add artificial intermediate steps
  • Track units explicitly throughout ("$10.00 - $6.00 = $4.00", not just "10 - 6 = 4")
  • Include a plausibility check in complex examples ("The answer 42 seconds is reasonable for a 100m sprint")
  • Use a consistent final-answer format across all demonstrations to enable reliable answer extraction
  • Ensure demonstrations cover diverse operations and problem structures to prevent operation-fixation bias
  • Write reasoning from the perspective of an expert solving the problem, not from the perspective of what the answer is
import openai
import re

client = openai.OpenAI()

def check_cot_faithfulness(question, answer_key):
    """Generate a CoT trace and verify reasoning is consistent with the answer."""
    msgs = [{"role": "system", "content": "Solve step by step. End with: The answer is [number]."},
            {"role": "user", "content": question}]
    resp = client.chat.completions.create(model="gpt-4o-mini", messages=msgs, max_tokens=300)
    trace = resp.choices[0].message.content.strip()
    match = re.search(r"The answer is ([\d\.]+)", trace)
    predicted = match.group(1) if match else "NOT FOUND"
    correct = str(answer_key) in predicted
    print(f"Question: {question[:60]}...")
    print(f"Predicted: {predicted}  |  Expected: {answer_key}  |  Correct: {correct}")
    print(f"Trace excerpt: {trace[:120]}...\n")
    return correct, trace

PROBLEMS = [
    ("If a car travels 45 mph for 1.5 hours, how many miles does it cover?", 67.5),
    ("A recipe needs 2.5 cups of flour per batch. How much for 3 batches?", 7.5),
    ("Sam earns $18/hr and works 35 hours. Tax is 20%. What is take-home pay?", 504),
]
results = [check_cot_faithfulness(q, a) for q, a in PROBLEMS]
accuracy = sum(r[0] for r in results) / len(results)
print(f"CoT accuracy on {len(PROBLEMS)} problems: {accuracy:.1%}")

Limitations and Failure Modes

Chain-of-thought prompting has several important failure modes that practitioners must understand. Hallucinated reasoning occurs when the model produces a plausible-sounding but internally inconsistent chain that leads to the wrong answer while appearing correct at each step. Studies find that 15–25% of wrong-answer CoT traces contain individually correct-looking steps that collectively lead to incorrect conclusions, making automated verification essential. Calculation errors in multi-digit arithmetic persist even with CoT, since the model still must predict each digit without an actual arithmetic unit; tool-augmented CoT (calling a calculator at arithmetic steps) addresses this but adds implementation complexity. CoT does not help small models (below roughly 100B parameters) because these models cannot reliably generate valid reasoning chains. Finally, CoT prompts consume significantly more output tokens per call — a 3-sentence reasoning chain before each answer multiplies output token cost by 3–5x, which matters at scale.

import openai

client = openai.OpenAI()

TASKS = [
    ("simple_arith", "What is 847 + 293?", "1140"),
    ("word_problem", "Lisa has 48 stickers. She gives a quarter to Maya and a third to Noah. How many left?", "28"),
    ("commonsense", "Would a wooden boat float in mercury?", "yes"),
    ("lookup", "What element has atomic number 6?", "carbon"),
]

def run_task(task_name, question, answer_key, use_cot):
    suffix = " Think step by step." if use_cot else ""
    msgs = [{"role": "system", "content": "Answer concisely. " + ("Show reasoning then answer." if use_cot else "")},
            {"role": "user", "content": question + suffix}]
    resp = client.chat.completions.create(model="gpt-4o-mini", messages=msgs, max_tokens=150)
    reply = resp.choices[0].message.content.strip().lower()
    correct = answer_key.lower() in reply
    mode = "CoT" if use_cot else "Direct"
    print(f"{task_name:15s} {mode:8s}: correct={correct}  reply_len={len(reply)}")
    return correct

for name, q, ans in TASKS:
    run_task(name, q, ans, use_cot=False)
    run_task(name, q, ans, use_cot=True)
    print()

Scale Requirement for CoT: CoT only reliably helps models with approximately 100 billion or more parameters. Smaller models tend to produce confident but incorrect reasoning chains, which can actually hurt accuracy compared to direct answering. If you are working with a smaller model (7B–13B parameters), test whether CoT helps on your specific task — if the model's reasoning chains are frequently wrong, you may be better off with direct few-shot prompting or fine-tuning.

CoT vs Fine-Tuning

Chain-of-thought prompting and supervised fine-tuning are complementary approaches that occupy different positions on the performance-cost curve. CoT requires no labelled data and no compute beyond inference, but is bounded by the base model's capability and consumes additional output tokens. Fine-tuning on CoT-annotated data (question + reasoning chain + answer) yields models that produce correct reasoning chains more consistently, generalise better to out-of-distribution problems, and do not require the few-shot examples in the prompt (reducing input token cost). The recommended approach is: start with zero-shot or few-shot CoT during prototyping; if CoT achieves acceptable accuracy, use it in production; if it does not, collect 200–2000 CoT-annotated examples for your task and fine-tune. Fine-tuning on CoT annotations typically achieves better accuracy than pure CoT prompting at smaller model sizes, enabling the deployment of smaller, faster, cheaper models with fine-tuning instead of large models with costly CoT inference.

  • CoT prompting: zero data cost, works immediately, bounded by base model capability and scale requirement
  • Fine-tuning on CoT data: higher upfront cost, better generalisation, enables smaller models for deployment
  • Hybrid: use CoT prompting on a large model to generate CoT annotations, then fine-tune a smaller model on them
  • Output token cost: CoT multiplies output tokens by 3–8x; at scale this is significant — budget accordingly
  • Debug advantage: CoT reasoning traces reveal exactly which step failed, making prompt improvement faster
  • For classification tasks, CoT often exceeds fine-tuning performance when the model is large enough (100B+)

Key Takeaways

Chain-of-thought prompting is the most impactful zero-data technique for improving LLM performance on multi-step reasoning tasks. By augmenting few-shot demonstrations with step-by-step reasoning traces, CoT enables models to decompose complex problems, track intermediate computations, and allocate generation capacity proportionally to problem difficulty. The gain is largest on arithmetic word problems, symbolic reasoning, and multi-hop commonsense tasks, where CoT can provide 30–40 percentage point improvements over direct answering. The technique is constrained by model scale (requires roughly 100B parameters), increases output token cost, and does not help on single-step tasks. The quality of CoT demonstrations is crucial — strong examples that decompose problems with explicit unit tracking and plausibility checks transfer better than shallow computation chains.

  • Augment each few-shot demonstration with a step-by-step reasoning trace that leads to the final answer
  • Use 3–8 demonstrations; each must include: problem decomposition, intermediate results, unit tracking, final answer
  • CoT is most effective on multi-step math, symbolic reasoning, and multi-hop commonsense — not single-step lookups
  • Requires approximately 100B parameters; test on your model size before committing to a CoT prompting strategy
  • Expect 3–8x more output tokens per call — budget for this in high-volume production systems
  • Use CoT faithfulness checking: verify that reasoning steps are consistent with the stated final answer
  • Consider fine-tuning on CoT annotations to get CoT-quality output from smaller, faster, cheaper models
