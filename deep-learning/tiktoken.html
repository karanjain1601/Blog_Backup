Tiktoken: OpenAI's Fast BPE Tokenizer

Tiktoken is OpenAI's open-source, Rust-backed BPE tokenizer released in 2023. It is the production tokenizer behind every OpenAI API call — every prompt you send to GPT-3.5-turbo or GPT-4 is tokenized by tiktoken before reaching the model. The library exposes a minimal Python API (pip install tiktoken) that wraps a highly optimised Rust core, making it 3–6× faster than equivalent HuggingFace tokenizer implementations and 5–20× faster than pure-Python BPE. Tiktoken implements byte-level BPE: the initial vocabulary consists of all 256 possible bytes, ensuring that any UTF-8 string can be encoded without an unknown token. Understanding tiktoken is essential for accurate prompt cost estimation, context-window management, and building chat-format requests that respect token budgets.

Overview

Tiktoken's design prioritises three goals: correctness (matching OpenAI's server-side tokenization exactly), speed (Rust core with Python bindings via PyO3), and simplicity (a small, stable public API). The library ships four named encodings — r50k_base, p50k_base, cl100k_base, and o200k_base — each corresponding to a specific vocabulary and regex pre-tokenizer. Encoding names map directly to model families: GPT-2 uses r50k_base; Codex uses p50k_base; GPT-3.5-turbo and GPT-4 use cl100k_base; GPT-4o and o1 use o200k_base. The key API entry points are tiktoken.get_encoding('name') to load by name and tiktoken.encoding_for_model('model-name') to resolve the correct encoding automatically from a model identifier. The encode() method returns a list of integer token IDs; decode() converts IDs back to bytes; encode_ordinary() skips special-token handling for speed.

Byte-Level BPE Foundation

Byte-level BPE starts from a vocabulary of 256 bytes (0x00–0xFF) rather than individual Unicode characters. This guarantees that any input text — regardless of language, script, or encoding — can be tokenized without producing an [UNK] token. Training proceeds identically to standard BPE: count all adjacent byte-pair frequencies across the training corpus, merge the most frequent pair into a new vocabulary token, and repeat until the vocabulary reaches the target size. For cl100k_base, this process produces 100,256 merge operations on top of the 256 base bytes, yielding the final 100,277-token vocabulary (including 21 special tokens). Because merges are applied in a fixed order, encoding is deterministic: the same string always produces the same token IDs on the same encoding, regardless of surrounding context or batching.

The performance advantage of tiktoken comes from its priority-queue encoding algorithm. Naive BPE encoding scans the token list for applicable merges on every step, giving O(M × T²) worst-case complexity per word where M is the number of merges and T is the input length. Tiktoken uses a Rust BinaryHeap to track candidate merges, reducing this to O(T log T) per sequence and enabling batch encoding of many sequences in parallel. In practice, tiktoken encodes roughly 1 million tokens per second on a single CPU core — fast enough that tokenization is rarely a bottleneck even in high-throughput serving scenarios.

Vocabulary Families

OpenAI has released four distinct encodings over the history of GPT models, each with a larger vocabulary and a refined pre-tokenization regex. r50k_base (50,257 tokens) is the GPT-2 encoding, identical to the vocabulary released by OpenAI in 2019. p50k_base (50,281 tokens) is a minor variant used by the Codex code-completion models; it adds 24 tokens for common programming constructs. cl100k_base (100,277 tokens) doubled the vocabulary size for GPT-3.5 and GPT-4, reducing average English fertility from ~1.4 tokens/word to ~1.25 tokens/word and significantly improving tokenization of non-English languages and code. o200k_base (200,019 tokens) was introduced with GPT-4o and further reduces fertility for multilingual text, with particular improvements for CJK scripts, Arabic, and structured data formats. Larger vocabularies reduce context-window consumption but increase embedding-matrix memory: at 1536 dimensions (GPT-4o), the embedding matrix alone is 200K × 1536 × 2 bytes ≈ 585 MB.

Regex Pre-tokenization

Before BPE merges are applied, tiktoken splits the input into pre-tokens using a regex pattern. This prevents BPE from creating cross-word tokens that depend on context — without pre-tokenization, 'the end' and 'theme nd' could share a common token 'e e' if that pair is frequent, making tokenization non-local. GPT-4's cl100k_base uses a 5-group regex pattern (distinct from GPT-2's 4-group pattern) that splits on: (1) contractions and possessives such as 's, 't, 're, 've, 'm, 'll, 'd; (2) optional-space + letter sequences; (3) optional-space + digit sequences; (4) optional-space + non-whitespace non-letter non-digit characters (punctuation, symbols); (5) whitespace-only tokens. The o200k_base encoding uses a nearly identical pattern with minor adjustments for extended Unicode character classes. Each pre-token is encoded independently, so merges never span a pre-token boundary.

The regex pre-tokenizer determines which token boundaries are possible. For example, a space before a word is merged into the word's token (as in GPT-2's Ġ prefix representation), rather than being a standalone token. Numbers are split so that multi-digit numbers like '2024' may become one token (if the merge exists) or multiple tokens ('20', '24'), but digits are never merged with surrounding letters. Punctuation sequences like '...' or '---' are kept together as single pre-tokens and encoded as one or two tokens. These design decisions significantly affect downstream model behaviour: models trained on cl100k_base learn that certain token boundaries always correspond to word or morpheme boundaries, which aids subword generalisation.

Encoding and Decoding

Tiktoken's encode() method returns a list of token IDs (integers). The decode() method takes a list of IDs and returns bytes (not a str), which must be decoded with .decode('utf-8', errors='replace') for display. This bytes-first design is intentional: individual token IDs may not correspond to valid UTF-8 strings when decoded in isolation, because a multi-byte Unicode character can be split across consecutive tokens. Decoding each ID independently would produce garbled output for any character whose UTF-8 encoding is split; decoding the full byte sequence at once is always safe. The encode_ordinary() method skips special-token handling and is slightly faster when inputs are guaranteed not to contain special token strings. The encode_batch() and decode_batch() methods process multiple sequences in parallel using Rust threads.

Special Tokens and Chat Formats

Special tokens are token strings that do not arise from BPE merges; they are added to the vocabulary at fixed IDs outside the BPE token range. cl100k_base defines five special tokens used by the ChatML format: <|endoftext|> (end of a document, ID 100257), <|fim_prefix|> (fill-in-the-middle prefix, ID 100258), <|fim_middle|> (ID 100259), <|fim_suffix|> (ID 100260), and <|endofprompt|> (ID 100276). GPT-3.5-turbo and GPT-4 chat completions use the ChatML format, which wraps each turn with implicit special tokens: <|im_start|>role\ncontent<|im_end|>. OpenAI's tiktoken documentation counts ~4 extra tokens per message (for the role wrapper) and ~2 tokens for the reply priming, which is why the standard token-counting formula adds a per-message overhead rather than encoding the chat structure directly.

Use encoding_for_model, not encoding name: Different OpenAI models use different encodings with different vocabulary sizes — always specify the encoding by model name (tiktoken.encoding_for_model('gpt-4')) rather than encoding name to avoid silent token count mismatches. For example, tiktoken.get_encoding('cl100k_base') and tiktoken.encoding_for_model('gpt-4') are currently equivalent, but if OpenAI updates gpt-4 to use o200k_base, encoding_for_model will automatically resolve the new encoding while the hardcoded string will silently use the old one, producing incorrect token counts and potentially truncated or oversized prompts.

Performance and Fertility

Fertility — average tokens per word — is the primary quality metric for a tokenizer's compression efficiency. Lower fertility means more text fits in a fixed context window and the model attends over shorter sequences for the same semantic content. For English prose, r50k_base achieves fertility ≈ 1.3–1.5, cl100k_base achieves ≈ 1.2–1.3, and o200k_base achieves ≈ 1.1–1.2. For code (Python, JavaScript), cl100k_base has fertility ≈ 1.1–1.4 because identifiers and keywords are common and receive dedicated tokens. For Chinese or Japanese, the improvement from cl100k_base to o200k_base is larger: common CJK characters that needed 2–3 tokens in cl100k_base fit in 1–2 tokens in o200k_base. Throughput benchmarks show tiktoken encoding English text at 1–2 MB/s on a single core, which is 3–6× faster than HuggingFace's PreTrainedTokenizerFast for equivalent BPE vocabularies, and 15–30× faster than pure-Python BPE implementations.

Token cost is directly proportional to the token count returned by tiktoken. As of mid-2025, GPT-4o charges $2.50 per 1M input tokens and $10.00 per 1M output tokens. A 1000-word English document encodes to roughly 1250–1350 cl100k tokens and costs approximately $0.003 per call at GPT-4o pricing. Understanding fertility helps prioritise tokenizer upgrades: switching a pipeline from gpt-3.5-turbo (cl100k) to gpt-4o (o200k) reduces token count by roughly 5–10% for English and 15–25% for mixed multilingual text, providing a cost reduction even before considering model quality differences.

Key Takeaways

  • Tiktoken is OpenAI's Rust-backed BPE tokenizer; it is 3–6× faster than HuggingFace tokenizers and 15–30× faster than pure-Python BPE.
  • Four encodings exist: r50k_base (50K, GPT-2), p50k_base (50K, Codex), cl100k_base (100K, GPT-3.5/GPT-4), o200k_base (200K, GPT-4o/o1).
  • Byte-level BPE guarantees zero OOV tokens — any UTF-8 input encodes without [UNK] because all 256 bytes are in the base vocabulary.
  • Always use tiktoken.encoding_for_model('model-name') rather than hardcoded encoding names to avoid silent vocabulary mismatches.
  • The cl100k_base 5-group regex pre-tokenizer prevents cross-word BPE merges by splitting contractions, letters, digits, punctuation, and whitespace independently.
  • Special tokens like <|im_start|> and <|im_end|> are added at IDs above the BPE range and must be explicitly allowed in encode() via allowed_special.
  • Fertility for English: r50k ≈ 1.4, cl100k ≈ 1.25, o200k ≈ 1.15 — each generation saves ~10% context-window space per token.
  • ChatML format adds ~4 overhead tokens per message; always include this in token-budget calculations for chat-completion APIs.
  • decode() returns bytes, not str — always call .decode('utf-8', errors='replace') on the result to handle split multi-byte characters safely.

Code Examples

The following code blocks demonstrate tiktoken's core API: basic encoding and decoding, the regex pre-tokenization pattern, multi-encoding comparison with fertility analysis, and custom special-token handling for chat formats.

import tiktoken

# Load cl100k_base — used by GPT-3.5-turbo and GPT-4
enc = tiktoken.get_encoding('cl100k_base')

# Basic encode / decode
text = 'Hello, world! Tiktoken is OpenAI\'s fast BPE tokenizer.'
token_ids = enc.encode(text)
print(f'Text   : {text}')
print(f'Tokens : {token_ids}')
print(f'Count  : {len(token_ids)} tokens')

# Decode back to string
decoded = enc.decode(token_ids).decode('utf-8')
print(f'Decoded: {decoded}')
assert decoded == text, 'Round-trip failed'

# Inspect individual tokens and their byte representations
print(f'\n{"ID":>7}  {"Bytes":<30}  {"Repr"}')
for tid in token_ids[:8]:
    token_bytes = enc.decode_single_token_bytes(tid)
    print(f'{tid:>7}  {str(token_bytes):<30}  {token_bytes.decode("utf-8", errors="replace")!r}')

# Count tokens for a chat message (GPT-4 ChatML format)
def count_chat_tokens(messages, model='gpt-4'):
    enc = tiktoken.encoding_for_model(model)
    n_tokens = 2  # reply priming: <|im_start|>assistant
    for msg in messages:
        n_tokens += 4  # per-message overhead: role wrapper tokens
        for value in msg.values():
            n_tokens += len(enc.encode(value))
    return n_tokens

messages = [
    {'role': 'system', 'content': 'You are a helpful assistant.'},
    {'role': 'user', 'content': 'Explain byte-level BPE in two sentences.'},
]
print(f'\nChat token count: {count_chat_tokens(messages)} tokens')

import tiktoken

# Compare all four tiktoken encodings on identical text
ENCODINGS = [
    ('r50k_base',   50_257,  'GPT-2, text-davinci-001/002'),
    ('p50k_base',   50_281,  'Codex, code-davinci-002'),
    ('cl100k_base', 100_277, 'GPT-3.5-turbo, GPT-4'),
    ('o200k_base',  200_019, 'GPT-4o, o1, o3'),

# Use a diverse test corpus: English, code, multilingual, and numbers
texts = {
    'English prose':  'The transformer architecture relies on self-attention mechanisms to model long-range dependencies.',
    'Python code':    'def softmax(x):\n    e = np.exp(x - x.max())\n    return e / e.sum()',
    'Mixed numbers':  'Pi is approximately 3.14159265 and e is 2.71828182845',
    'CJK text':       '\u4eba\u5de5\u667a\u80fd\u6a21\u578b\u5728\u81ea\u7136\u8bed\u8a00\u5904\u7406\u4e2d\u8868\u73b0\u51fa\u8272',

print('-' * 120)
for enc_name, vocab_size, used_by in ENCODINGS:
    enc = tiktoken.get_encoding(enc_name)
    counts = {label: len(enc.encode(t, disallowed_special=())) for label, t in texts.items()}
    row = '  '.join(f'{c:>5}tok' for c in counts.values())
    print(f'{enc_name:<16} {vocab_size:>8,}  {used_by:<28}  {row}')

# Compute fertility (tokens per word) for English
print('\nFertility (tokens/word) for English prose:')
words = texts['English prose'].split()
for enc_name, vocab_size, _ in ENCODINGS:
    enc = tiktoken.get_encoding(enc_name)
    tok_count = len(enc.encode(texts['English prose'], disallowed_special=()))
    fertility = tok_count / len(words)
    print(f'  {enc_name:<16} {tok_count:>3} tokens / {len(words)} words = {fertility:.3f} tokens/word')

import tiktoken

# Define a custom encoding with additional special tokens for chat
# cl100k_base uses these for the ChatML format internally
base_enc = tiktoken.get_encoding('cl100k_base')

# Add custom chat separator tokens on top of cl100k_base
chat_enc = tiktoken.Encoding(
    name='cl100k_chat',
    pat_str=base_enc._pat_str,
    mergeable_ranks=base_enc._mergeable_ranks,
    special_tokens={
        **base_enc._special_tokens,
        '<|im_start|>': 100264,
        '<|im_end|>':   100265,
    },
)

print(f'Base vocab size    : {base_enc.n_vocab}')
print(f'Chat vocab size    : {chat_enc.n_vocab}')
print(f'<|im_start|> id   : {chat_enc.encode_single_token("<|im_start|>")}')
print(f'<|im_end|>   id   : {chat_enc.encode_single_token("<|im_end|>")}')
print()

# Encode a full ChatML conversation including special tokens
conversation = (
    '<|im_start|>system\n'
    'You are a helpful assistant specialising in tokenization.\n'
    '<|im_end|>\n'
    '<|im_start|>user\n'

    '<|im_end|>\n'
    '<|im_start|>assistant\n'
)
