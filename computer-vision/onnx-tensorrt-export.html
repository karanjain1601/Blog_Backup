ONNX and TensorRT Export: Deploying Vision Models at Inference Speed

Overview

Deploying vision models in production requires moving beyond PyTorch eager mode into optimized runtimes. ONNX provides a portable intermediate representation, while TensorRT compiles that representation into hardware-fused GPU kernels. Together they form a two-stage pipeline: export once to ONNX, then compile a platform-specific TensorRT engine for each target GPU.

This note covers the full export and compilation pipeline: ONNX export with dynamic axes, TensorRT engine building with FP16 and INT8 precision modes, INT8 calibration workflows, and practical latency profiling techniques to verify that each optimization delivers measurable gains before it is promoted to production serving.

ONNX Export from PyTorch

torch.onnx.export traces the model with a dummy input and records every tensor operation into the ONNX graph. Setting opset_version=17 ensures access to the latest standardized operators. Dynamic axes let the exported graph accept variable batch sizes at runtime without re-exporting, which is critical for serving workloads with unpredictable concurrency.

import torch

model.eval()
dummy_input = torch.randn(1, 3, 224, 224).cuda()
torch.onnx.export(
    model,
    dummy_input,
    "model.onnx",
    opset_version=17,
    input_names=["image"],
    output_names=["logits"],
    dynamic_axes={"image": {0: "batch"}},
    do_constant_folding=True,
)

After export, validate the graph with onnx.checker.check_model and run a sanity check using onnxruntime to confirm outputs match PyTorch within floating-point tolerance. Common failure modes include custom operators not mapped to ONNX primitives and control flow branches that cannot be statically traced during export.

TensorRT Engine Building

TensorRT's builder API parses the ONNX graph and applies layer fusion, kernel autotuning, and precision lowering. The EXPLICIT_BATCH flag is required for all modern networks — it exposes the batch dimension to the optimizer, enabling further fusion across batch-level operations. Setting max_workspace_size controls scratch memory available during autotuning.

import tensorrt as trt
logger = trt.Logger(trt.Logger.WARNING)
builder = trt.Builder(logger)
network = builder.create_network(
    1 << int(trt.NetworkDefinitionCreationFlag.EXPLICIT_BATCH)
)
parser = trt.OnnxParser(network, logger)
parser.parse_from_file("model.onnx")
config = builder.create_builder_config()
config.max_workspace_size = 1 << 30  # 1 GB
engine = builder.build_engine(network, config)

Serialize the built engine with engine.serialize() and save it as a .plan file. Deserializing at serving time costs only milliseconds compared with the minutes-long build step. Always store the engine alongside the source ONNX file and rebuild only when model weights, architecture, or target GPU generation changes.

INT8 Calibration for TensorRT

INT8 quantization halves memory bandwidth and enables faster integer arithmetic units, but requires a calibration step to determine the optimal per-tensor quantization scale. The calibrator runs a representative sample of real data through the FP32 network and records activation histograms, which TensorRT uses to minimize quantization error across all layers.

config = builder.create_builder_config()
config.set_flag(trt.BuilderFlag.FP16)
config.set_flag(trt.BuilderFlag.INT8)
config.int8_calibrator = MyCalibrator(
    calib_loader,
    cache_file="calib.cache"
)
config.max_workspace_size = 1 << 30
engine = builder.build_engine(network, config)

The calibration cache stores computed scales so subsequent builds skip the data-pass entirely. Always validate INT8 accuracy against your full evaluation set after calibration. Layers sensitive to quantization error can be forced to run in FP16 by marking them individually: network.get_layer(i).precision = trt.DataType.HALF.

Profiling and Debugging

Profiling TensorRT inference requires CUDA-aware timing that synchronizes the GPU before reading the clock. Python time.time() measures wall time including scheduling jitter, CUDA kernel submission latency, and Python GIL contention — none of which reflects actual kernel execution. Use CUDA events or nsys profile for accurate per-layer attribution.

import numpy as np

times = []
with torch.cuda.profiler.profile():
    for _ in range(100):
        output = trt_infer(engine, input_data)
        torch.cuda.synchronize()
        times.append(measure_event_time())

p50 = np.percentile(times, 50)
p99 = np.percentile(times, 99)
print(f"p50={p50:.2f}ms  p99={p99:.2f}ms")

For production monitoring, instrument your serving container with histogram metrics — p50, p95, and p99 — rather than averages. A 5% tail at p99 can represent thousands of SLA violations per hour in high-QPS deployments. Correlate latency spikes with GPU utilization, memory bandwidth saturation, and PCIe transfer overhead.

Key Takeaways

warning: TensorRT engines are hardware-specific — an engine built on an A100 will not run on a T4. Always rebuild engines on the target deployment hardware. Cache the engine file (.plan) and rebuild only when the model or target GPU changes.

Export with opset_version=17 and dynamic axes to future-proof the ONNX artifact. Validate ONNX outputs against PyTorch with absolute tolerance less than 1e-4 before investing in TensorRT compilation. FP16 typically recovers 2x latency over FP32 with negligible accuracy loss; INT8 adds another 1.5-2x but demands careful calibration and accuracy re-validation.

Profile with CUDA events, not Python timers, and always report p99 latency alongside mean. Target-specific TensorRT builds are non-portable — maintain a rebuild pipeline triggered by GPU type changes in your deployment environment. Document the hardware, driver version, and TensorRT version used for each engine in your model registry.
