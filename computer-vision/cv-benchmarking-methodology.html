CV Benchmarking Methodology: Reproducible Accuracy and Latency Measurement

Overview

Benchmarking a vision model without rigorous methodology produces numbers that cannot be reproduced, compared, or trusted in production capacity planning. The two primary axes are accuracy — measured on a held-out evaluation set with standardized preprocessing — and latency, measured with proper GPU warmup, synchronization, and statistical reporting.

This note covers reproducible measurement protocols for both axes, profiling tools that provide per-operator attribution, and reporting standards that communicate results clearly enough for another engineer to reproduce them on different hardware — without relying on undocumented assumptions about batch size, precision, or warmup state.

Accuracy Benchmarking

Accuracy benchmarking must use the same preprocessing pipeline that the model was trained with. Off-by-one errors in crop size, interpolation mode (bilinear vs. bicubic), or normalization constants silently reduce accuracy by 0.5-2 percentage points. Pin the exact torchvision transform used during training and apply it identically during evaluation.

Evaluate on the full validation split, not a random subset, and report top-1 and top-5 accuracy for classification tasks. For detection, report mAP at IoU 0.50 and 0.50:0.95. For segmentation, report mIoU. Always specify the dataset name, split, and any class exclusions in the benchmark report so reviewers can reproduce the number exactly.

Mixed-precision evaluation (AMP) can alter accuracy for borderline predictions close to the decision boundary. Run full FP32 and FP16 evaluations separately, report both, and flag any model where the FP16 drop exceeds 0.2 percentage points — it likely has numerically sensitive layers that need selective precision assignment in your deployment plan.

Latency and Throughput Measurement

Accurate GPU latency measurement requires three things: a warmed-up device (GPU caches, JIT paths, and clocks at operating frequency), CUDA event timing (not wall-clock), and explicit synchronization before reading the timer. Omitting any of these produces latency numbers 20-40% lower than what production workloads actually observe at steady state.

import torch

model.eval()
dummy = torch.rand(1, 3, 224, 224).cuda()

# Warmup: flush JIT compilation and CUDA init
with torch.inference_mode():
    for _ in range(50):
        model(dummy)

torch.cuda.synchronize()
print("GPU warmed up — begin timing")

import torch

times = []
x = torch.rand(1, 3, 224, 224).cuda()
for _ in range(200):
    start = torch.cuda.Event(enable_timing=True)
    end   = torch.cuda.Event(enable_timing=True)
    start.record()
    model(x)
    end.record()
    torch.cuda.synchronize()
    times.append(start.elapsed_time(end))

Run at least 200 timed iterations to obtain a stable distribution. Report median (p50) as the typical case and p99 as the worst-case SLA budget. Standard deviation and max latency should also be logged for capacity planning. A tight p50 with a high max indicates transient interference from other GPU workloads or system-level preemption.

import time

model.eval()
start = time.perf_counter()

with torch.inference_mode():
    for batch in loader:
        x = batch["image"].cuda()
        model(x)
    torch.cuda.synchronize()

elapsed = time.perf_counter() - start
throughput = len(dataset) / elapsed
print(f"Throughput: {throughput:.1f} img/s")

Include data loading and preprocessing in throughput measurements only if those stages are on the critical path. If preprocessing is async or pre-cached, exclude it and note the distinction explicitly. Always report GPU model, driver version, CUDA version, and batch size alongside throughput numbers — they are meaningless without that hardware context.

Profiling Tools

NVIDIA Nsight Systems (nsys) provides a timeline view of CPU and GPU activity, revealing pipeline gaps, synchronization stalls, and inefficient kernel scheduling. NVIDIA Nsight Compute (ncu) gives per-kernel roofline analysis showing whether a layer is memory-bandwidth-bound or compute-bound — the key input for deciding which optimization to pursue next.

import timm
from torchvision.models import resnet50, ResNet50_Weights

model = resnet50(weights=ResNet50_Weights.IMAGENET1K_V2)
model = model.cuda().eval()

results = timm.models.benchmark(
    model,
    batch_size=256,
    input_size=(3, 224, 224),
    amp=True,
    device="cuda",
)
print(results)

PyTorch Profiler (torch.profiler.profile) integrates directly into the training loop and exports Chrome trace JSON for visualization. The with_stack=True option adds Python stack frames to every CUDA event, making it possible to map slow kernels back to specific model layers and even source-code lines without leaving the Python environment.

Reporting Standards

Metric Tool What It Measures Pitfall
Top-1 accuracy torchvision eval Classification correctness Dataset split leakage
Latency p50/p99 CUDA events Per-sample inference time Cold start, no warmup
Throughput time.perf_counter Images per second Excludes data loading
FLOPs ptflops / fvcore Compute complexity Ignores memory bandwidth
Memory peak torch.cuda.max_memory VRAM allocation Does not include host RAM
Energy (mJ) NVML / perf Power per inference Varies with clock throttle

A complete benchmark report must include: hardware spec (GPU model, VRAM), software stack (PyTorch, CUDA, driver versions), model config (architecture, checkpoint, precision), input spec (resolution, batch size, color space), and evaluation protocol (warmup iterations, timed iterations). Missing any field makes the number non-reproducible by others.

Automate report generation from structured JSON or YAML — never rely on hand-typed tables in documents. Store benchmark results in a time-series database or experiment tracker alongside the model checkpoint hash, so regressions appear immediately when a new version is evaluated and can be bisected to the exact commit that caused them.

Key Takeaways

warning: Never report mean latency alone — report p50 and p99. Mean latency hides tail spikes (JIT, GC, preemption) that cause SLA violations in production. Always warm up the GPU for at least 50 iterations before timing, and use CUDA events not Python time.time().

Structure benchmarking as a repeatable pipeline: warmup, then timed iterations, then synchronize, then compute percentiles, then report with full hardware context. Separate accuracy benchmarking (full validation set, full precision) from latency benchmarking (timed iterations, target precision) and run both automatically for every model version update.

Store all benchmark artifacts — raw timing arrays, profiler traces, and accuracy logs — alongside model checkpoints in your artifact store. This makes it possible to retroactively investigate why a production model's latency differs from the benchmark, which is almost always due to a difference in environment, batch size, or precision mode.
